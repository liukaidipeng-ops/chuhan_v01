# 电脑（AI）开发手册

给以后做新模式的电脑用：电脑是怎么搭的、手里有哪些工具、一个改动从想法到上线怎么走、怎么判断“真的变强了”、踩过哪些坑。
内容来自技能模式（楚汉·兵法）电脑 2026-10 的开发。合格标准另见 `docs/bfai-qualification.md`；逐日记录见仓库根目录 `NOTES.md`；和 TD 的往来见 `docs/collab/`。

---

## 1. 先说清楚：这不是“训练神经网络”

技能模式的电脑是 **搜索 + 人写的估值公式**：
- 往后算几步（搜索），每个算到底的局面用公式打分（估值）。
- 变强靠两条：**算得更深 / 更准**（搜索），和 **分数给得更对**（估值）。

所谓“培训电脑”，在这里就是：找到它哪里笨 → 改搜索或估值 → 用大量对局证明真的变强 → 上线。

### 1.1 要不要训练神经网络（用户 2026-10-09 问过）
- **照“阿尔法零”从零自学：不现实。** 要显卡跑几百万局自对打；我们只有 GitHub 免费机器（普通处理器），霸王一局要几分钟，差上千倍。规则一改还得重训。
- **分三步走：**
  1. **自动调现有公式的权重**（`tools/tune/`，2026-10-09 开始）：打分公式拆成“特征 × 权重”（81 项，原权重下和线上逐个相等），
     自对打收“安静局面 + 终局胜负”，用逻辑回归反推每个权重（国际象棋界叫 Texel 调参）。等于只有一层的网络，便宜，大部分好处在这一步。
     **结果（2026-10-10）：第一轮（3802 局校尉自对打、16 万个局面，检验误差 −6.5%）对同底版霸王 83%、校尉 84%（各 600 局）——比所有搜索改动加起来都大。**
     加 11 个潜力特征（第七版的想法）−7.1%、霸王 85.6%。上线写法：`tools/tune/score_w.js` 把权重写回原公式（不慢；特征版慢 36%），`make_patch.js` 出补丁。
     下一轮：用新权重自对打收数据（t4）、加新特征（技能就绪、贴帅子数、逼到家门口），再拟合；每轮都要对线上对打确认。
  2. 第 1 步有效，再训一个**小网络当打分公式**（搜索不变，只换打分；国际象棋最强的引擎现在就是这样）。
  3. 网络必须**很小、很快**才能放进网页：打分一慢就少算几层，反而变弱（“算深”最值钱，见第 7 节）。
- 代价：网络是黑箱（复盘拆不开分数）；规则一改要重训，手写公式改一行就行。

## 2. 电脑的结构（`src/bfai.js`）

| 部分 | 作用 | 要点 |
|---|---|---|
| 档位 `LEVELS` | 新兵 / 校尉 / 霸王 | 校尉最多 3 层；霸王最多 7 层，网页里按时间（每步约 3 秒）收手。测试时用 `nodes`（按搜索量收手），结果可复现、和机器快慢无关 |
| 根节点 `think()` | 列出这一步所有走法（含“先升级再走”、兵法），逐层加深，选分最高的 | 根上的升级候选有筛子（`upgradeCands`：前 3 名 + 救命的 + 一个解锁技能的；快攒够钱升车时只肯升车） |
| 搜索 `ab()` | αβ 剪枝 | 将军延伸、危险延伸（自己的帅被堵、对方砍不死的子要贴脸）；对方“先升级再走”只在第 1 层、只看静态收益前 3 名；破釜沉舟 / 背水一战另算 |
| 吃子搜索 `qs()` | 算到底时把“谁会被白吃”算清 | 每层最多 6 个吃子；占搜索时间约 45% |
| 估值 `score()` | 给局面打分 | 子力（血量最要紧）、位置、贴脸杀势、军功、兵法还没用、终极兵法、决战。复盘工具能把分数拆成这几项看 |
| 一步杀保险 | 选定后查对方能不能一步将死（含先升级），能就换 | 2026-10 上线 |
| 记表 + 靠后着法少算一层 | 提速 | 2026-10 交 TD（C61），只在霸王用后者 |

**引擎（`src/bingfa.js`、`src/rules.js`，TD 的）占了大部分时间**：走一步要复制整个局面、生成走法、判断将军。剖析过一次：电脑自己的搜索代码不到 10%。想提速先剖析（见 4.7）。

## 3. 工具箱

| 工具 | 干什么 | 常用写法 |
|---|---|---|
| `tools/bfsim.js` | 两个电脑对打，换边、按种子可复现 | `node tools/bfsim.js --games 300 --seed 3000 --level hard --nodes hard=100000 --ai-r 新.js --ai-b git:提交号` |
| GitHub 模拟（`tools/simjobs/*.json` → `.github/workflows/bfsim.yml`） | 免费机器上并行跑大批对打，结果自动提交到 `tools/simresults/` | 推一个 json：`args`、`env`（变体的开关）、`chunks`（分几段）。**一次只推一批**（最多占 12 个任务位，给网站发布留位置）。仓库是公开的，分钟数不限 |
| `tools/simpair.js` | 两组同种子对打逐局比 | `node tools/simpair.js 对照.json.gz 新组.json.gz` |
| `tools/bfai_exam.js` | 考卷：固定局面，看电脑走得对不对 | `node tools/bfai_exam.js a.js b.js --level hard --runs 3 --nodes hard=100000 [--only 关键字] [--lint]` |
| `tools/game2exam.js` | 把用户导出的对局里某一步收成考题 | `--turn 17汉 --add --name 名字 --mode same/avoid/survive/nomate` |
| `tools/review/review.js` | **复盘（第二版，2026-10-10 起用这个）**：按导出的版本号找当时那份引擎和电脑；用 TD 的正式观察接口（`BFAI.trace` 思考记录、`scoreParts`、裁判开关 `upAll` / `rootUpAll` / `fixedDepth`，C62 / H54），不打补丁。导出里有网页那次的真实思考记录就用它（算了几层、为什么停、候选和预想线、被筛掉的升级和原因、随机、一步杀保险），老导出按节点数重算。每步：深 / 宽裁判同层数比分、精确查一步杀、错因、估值拆分、“没料到”（自己的分一步掉 2 分以上）、Ham 的“这步笨”标记 | `node tools/review/review.js 对局.txt [--fast] [--md 报告.md] [--json 明细.json] [--branch i]` |
| `tools/review/decode_issue.js` | 读「对局」工单（TD 的“存并发给数值部”）：json / gzip+base64 / 拆成几块的都能还原成导出格式 | `node tools/review/decode_issue.js 工单.txt --out 对局.txt` |
| `tools/dumbgames/trace_game.js` | 旧版复盘（给电脑打文字补丁，TD 一改代码就断）；只留着复盘 C62 之前的老版本 | `BFAI_TR_BASE=提交 node tools/dumbgames/trace_game.js 对局.txt` |
| `tools/dumbgames/depth_cmp.js` | 同样搜索量下各版本平均算到几层、用多少节点 | `LV=hard NODES=100000 node tools/dumbgames/depth_cmp.js 目录 live 版本…` |
| `tools/dumbgames/fast_eq.js` | 提速验收：固定层数下根上每步的分是否和原版逐个相同 | `node tools/dumbgames/fast_eq.js 4 3` |
| `tools/perf/` | 引擎提速的核对和测速 | 见其中 README |
| `tools/bfpage_timing.js` | 真实网页里每步耗时、算到几层 | `--ai 文件 --level hard --side b --games 2` |
| `tools/tune/feats.js` | 打分公式拆成特征 × 权重；局面压缩 / 还原 | `feats(S, BF.ai, BF.CFG)`、`W0`、`pack` / `unpack` |
| `bfsim.js --dump-pos` | 对打时收“安静局面”（自己这步和对方下一步都没打到子、走前没被将军）+ 终局胜负 | 数据批：`tools/simjobs/t1-data-mid.json` |
| `tools/tune/fit.js` | 拟合权重：先定 K，再调权重；每五局留一局检验；`--check` 全量核对原权重 = 线上 | `node tools/tune/fit.js 结果.json.gz --out tools/tune/w_t1.json` |
| `tools/tune/score_w.js`、`make_patch.js` | 权重写回原公式（结构、分项不变）；生成给 TD 的补丁 | `node tools/tune/make_patch.js tools/tune/w_t3p.json` → `tools/variants/bfai_tune.patch` |
| `tools/variants/bfai_tuned.js` | C61 的电脑换上调出来的权重（`BFAI_TUNE_W`），拿去对打 | `--ai-r tools/variants/bfai_tuned.js --ai-b tools/variants/bfai_c61.js` |
| 变体生成器 `tools/variants/bfai_*.js` | 不动 `src`，按文字锚点给线上电脑打补丁、用环境变量开关；`make(开关, 名字)` 能在同一进程里生成两份（对打时一边陪练一边待测） | `bfai_fast.js`（提速）、`bfai_upfix.js`（升级盲区、陪练）、`bfai_trace.js`（复盘：预想线 + 估值拆分 + 裁判） |

考卷的判法：`same`（必须走某步）、`avoid`（别走原来那步）、`survive`（走完对方深搜找不到必胜）、`nomate`（走完对方没有一步杀，精确枚举）、`judge`（复盘裁判按固定层数算走完的局面，不比最好那步差 0.5 分以上）。

## 4. 标准流程：一个改动从想法到上线

1. **找问题**：用户导出的笨棋 → `trace_game.js` 复盘 → 分清是“算浅了”“没考虑到（被筛掉）”“对手的升级没看见”还是“分数给错了”。
   同时看“意外”：电脑这一步的分 → 对方走完后下一步的分，一下掉很多就是它没料到的地方，再看对方实际干了什么。
2. **写变体**：在 `tools/variants/` 按文字锚点改，开关默认关；关着时必须和原版逐字相同。
3. **先量代价**：`depth_cmp.js` 看同样搜索量少算了多少层；“结果应该完全相同”的改动用 `fast_eq.js` 证明。
4. **考卷**：不能在基础类别退步；少量分差先查是不是单双数层（见 5.3）。
5. **对打**（GitHub）：对线上电脑，同种子换边，**至少 600 局**；看得分和 z（|z| ≥ 2 才算数）。对真人有用、对电脑未必显出来的改动，再加一组对“会用这招的陪练”。
6. **一次只改一项**；几项都好再合起来测，合起来要比单项好才交。
7. **网页实测**：最长一步不能变慢太多。
8. **出干净补丁**（从变体生成的文件和线上 `src` 求差），在最新 dev 上 `git apply --check`，打上后跑 TD 全部测试。
9. **写 C 单**给 TD：改了什么、为什么、数据（对打、考卷、耗时、测试），没交的和原因。上线时机 TD 和用户定。

---

## 5. 判断“真的变强了”

1. **对打得分 + z**：600 局的误差约 ±4 个百分点；z ≥ 2 才算真变强，z ≤ −2 是真变弱，中间算不出差别。
2. **同种子逐局比**比两组总分更准：只看结果不同的那些局，净多赢多少。
3. **考卷只当标尺**，不当裁判：单个题受“算到单数层还是双数层”影响很大（例：考卷第 1 题，原版固定 4、5 层都走错，6 层才对）。
4. **复盘裁判比分必须同层数**：最好那步和实走那步，走完后各按同样固定层数算（原来一边根上 4 层、一边走完 5 层，差距被夸大，报过错数）。

## 6. 踩过的坑（照着避开）

| 坑 | 教训 |
|---|---|
| 只拿电脑对电脑测“料到对手升级” | 线上电脑自己很少这样用升级，测不出对真人的价值；要加“会用升级的陪练”（`bfai_spar.js`） |
| 只给对手加升级、自己不加 | 电脑变得过分悲观；升级建模要两边对称 |
| 任何“多考虑几种着法”都吃深度 | 复杂中局只算 2～3 层时，加宽一点就少算一层，常常得不偿失。先提速再加宽 |
| 被将军时所有升级都试 | 这个游戏将军很常见，太贵（平均 3.37 → 3.08 层）；精准版也拖后腿 |
| 几项一起测 | r22 合起来 53.7%，拆开才知道只有“少算一层”有用、“被将军升级”拖后腿 |
| 记表（同一局面不重算） | 每枚子带击杀数、甲片、冷却，同一局面很少重复，只省 6% |
| 缓存“是否被将军” | 引擎有地方算完还改同一个棋盘，缓存会错；必须拿随机对局 + 搜索里逐次核对 |
| 网页实测工具用 file:// 打开页面 | 声音文件读不到会报错，不影响电脑耗时 |
| 等结果的后台程序 | 最多跑 4 小时，会被停；GitHub 霸王档 600 局要 2 小时以上 |
| 大模型多代理工作流（Fable） | 太耗额度；只在真需要时用、先说成本 |
| 拿“换了算法、分数理论上相同”的版本逐局比对打 | 浮点数相加顺序不同，分数差 1e-14，打平的两步会选得不一样，整局就分岔了。核对要逐个局面比分数（`fit.js --check`），不能比整局 |
| 一次推太多段 | GitHub 一次最多 256 段（matrix 上限），超了整批不开跑、两分钟就“失败”（r25）。`ci_sim.js plan` 现在会直接报错 |
| 规则一天改几次 | 老对局要用当时的引擎才重放得了：`review.js` 按导出版本号到 main 的 version.json 历史里找部署提交；变体按文字锚点打补丁，TD 改了写法就要跟着改（H54 改了 score / upgradeCands 的写法） |
| 校尉不写 `--nodes` | 校尉按时间收手（2.5 秒），机器快慢会影响结果；要复现就写 `--nodes mid=60000` |

## 7. 决策记录（2026-10，技能模式）

| 改动 | 数据 | 结论 |
|---|---|---|
| 一步杀保险 | 对线上 50.0%（600 局，不吃亏）；考卷修好“升卒贴脸一步杀” | 上线 |
| 对手第 3 层也能升级 + 离帅近的升级多给名额 | 对线上 45.2%（算浅：2.80 → 2.66 层） | 不交 |
| 精准版（只看会改变吃子结果的对手升级） | 对陪练 55.2%（不显著），对线上 45.8% | 不交 |

| 记表 | 固定层数分数逐个相同，只省 6% | 随提速一起交（给排序用） |
| 靠后安静着法少算一层（霸王） | 霸王 600 局 57.6%（z 3.8）；网页每步 1.8 秒、最长 3.7（原 2.2、6.0）；校尉只更快不更强 | C61 交 TD |
| 吃子搜索里全赚也追不上的不试 | 和不加一样 | 不交 |
| 根上自己的关键升级 | 和不加一样（57.2%） | 不交 |
| 被将军时多试升级 | 53.7%，拖后腿 | 不交，等提速更多后再试 |

| 第七版“长计划”的“活到兑现”推演 | 帮汉（+29 局）害楚（−30 局） | 并到 C61、只在执汉时开（`bfai_v7c61.js`），r24 对打中 |
| 让一步试试（空着裁剪） | 霸王同搜索量 4.02 → 4.15 层，87 个局面 86 个同一步 | 收益太小，不单独对打 |

## 8. 新模式起步清单

1. 规则引擎先有完整测试（走法、胜负、每个技能），并且**结果可复现**（同样的行动序列结果永远相同）。
2. 电脑先用现成框架：αβ + 逐层加深 + 吃子搜索 + 档位；新模式特有的动作（升级、技能、兵法）先进根节点、再决定要不要进搜索内部。
3. 估值先只放子力，跑通对打，再一项项加，每项都对打验证。
4. 先建好三样再优化：对打（`bfsim` + GitHub）、考卷（每个新规则至少一道“会不会用”、一道“会不会防”）、复盘（`trace_game`）。
5. 让用户导出笨棋，按第 4 节的流程修。
6. 提速前先剖析（`node --cpu-prof`），看时间到底花在哪。

## 9. 还没做的（按值不值排）

1. 继续提速（引擎复制局面、走法生成；搜索里更好的排序），把深度余量留给 2、3。
2. 两边对称地料到对手升级（等深度够了再加）。
3. 第七版“长计划”并进线上电脑（会为羁绊、升级攒钱、摆阵）。
4. 自动调估值权重（电脑自己对打调参）：工具已建好（1.1 节），数据批 t1 在跑。
