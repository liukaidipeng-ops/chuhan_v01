## P4（10-10）美术总监 V10 打开页面慢：法线图改成空闲时算，画面不变

**来由**：美术总监 V10（棋子刻字 + 贴地暗影，Ham 已批）请优化部看开页面的耗时。V10 在开局时给 32 颗子每颗现算一张 512 的法线图。

**量到的问题**（手机 390×844、画质中、CPU 降速 4 倍；`dev` c9cb6e1，两次）：
| | 未打 V10 | 打 V10 | V10 + P4 |
|---|---|---|---|
| 打开到能玩 | 31 / 31 秒 | **65 / 66 秒** | **16 / 16 秒** |
| 打开时最长一次卡死 | 1.5 秒 | **37 秒** | 1.5 秒 |
| 开局（startGame 后 10 秒）最长卡顿 | 0.4 秒 | 2.3～2.8 秒 | 0.4～0.5 秒 |
| 每帧绘制 | 260 | 291 | 291（V10 多 32 片暗影，各一个材质；在预算内） |

原因有两个：
1. 每颗子要从画布读 5 次像素（`getImageData`）。画布默认在显卡上，读一次要等显卡；32 颗共 160 次。
2. 两遍 512×512 的逐像素循环。

不降速时，这两项加起来多出约 2.7 秒，手机上要更久。

**改什么**：补丁 `perf/P4-lazy-facenorm.patch`，**打在 V10 之上**，只改 `board.js`，+28 −3 行。
1. `mkCanvas` 建画布时带 `{ willReadFrequently: true }`，画布放在内存里，读像素不用等显卡。这个函数造的画布都是要读像素的（法线、花纹），顺带让原有的银、金、玉花纹也变快：上表“V10 + P4”比“未打 V10”还快。
2. 木字面的法线图先挂一张 1×1 的平法线。画出来和没有法线图一样，用的又是同一个着色器，后面换图不用重新编译。然后每 30 毫秒抽空算 25 毫秒，一颗一颗算好再换上。页面刚开时大厅盖着棋盘，看不见。算好的照旧按 id 缓存。揭棋翻面、换兵种时，排队中的旧任务会作废。

**核对**：
- 开局 10 秒后，32 颗子全部换上了真法线图（真 32 / 平 0 / 无 0）。
- 近景截图 V10 对 V10 + P4（`perf/P4-near.jpg`，上 V10、下 P4）：刻字、圈线一样，只有格线红光的位置不同（动画时刻不同）。
- 测试：在 `dev` + V10 + P4 上，8 项测试全过。

**给 TD**：V10 已经上线（2026.10.10-428d9c，没带 P4）。P4 在最新 `main`（98a76c6）上 `git apply --check` 干净，可以直接接。

**线上版本复测**（`main` 98a76c6，降速 4 倍）：
| | 现在线上 | 线上 + P4 |
|---|---|---|
| 打开到能玩 | 68 秒（中间一次 38.6 秒卡死） | 34～35 秒（三次） |
| 打开页面的长任务合计 | 64.6 秒 | 35 秒 |
| 开局（技能模式）最长卡顿 | 0.5 秒 | 4.7～5.8 秒，见下 |
| 开局 10 秒主线程合计 | 10.1 秒 | 10.6 秒 |

开局那次卡顿不是 P4 本身造成的。采样显示它是原有的 `prewarmSkins`（第一局技能模式开局 1.5 秒后预做升级皮肤）里 `studioEnv → pmrem`，在同步等着色器编译（`getProgramParameter`）。没打 P4 时，这段等待被一百多次读像素盖住了（显卡那边边读边编完）；P4 让读像素变快，它就单独露出来了。软件渲染编着色器特别慢，真手机上这一下应该短得多。如果想再稳一点（TD 定）：可以把 `prewarmSkins` 挪到大厅空闲时做，或者 `pmrem` 前先 `compileAsync`。

**给美术总监**（不在补丁里）：V10 的 `blurred()` 用的是画布 `ctx.filter`。较老的 iOS Safari（大约 17 及以前）不支持，会直接不模糊。刻痕边会硬一点，但不会出错。请在 Ham 的 iPhone 上看一眼刻字的边是不是你要的样子。

## P2（10-10）对局静止时省电降到每秒 15 帧

**拍板**：Ham 10-10 12:27 在优化部审批台 perf-001 选「乙1 每秒 15 帧」。美术总监同意，意见见下面第 3 条。

**改什么**：`src/core.js` 主循环一处，补丁 `perf/P2-eco-15fps.patch`。只在省电开着（手机默认）、而且“静止”的时候生效。静止的意思是：最近 1.5 秒没碰屏，没有演出，镜头不动。
1. 静止时最短帧间隔 31 → 64 毫秒，也就是 30 帧 → 15 帧。一碰屏、走子、演出、结算都照旧满帧。
2. 一帧最多推进的时间：省电时 0.05 → 0.1 秒。不放宽的话，15 帧时每帧 0.067 秒会被截短，背景动画会慢下来。不开省电的照旧是 0.05 秒。
3. 静止时故意少画的帧，不算进帧时间统计。否则 `main.js` 的“自动降画质”（平均每帧超过 40 毫秒就降）会在静止 10 秒后把画质误降到“低”。

**改前 → 改后**（手机 390×844、画质中、CPU 降速 4 倍，只计数不真画，最新 `main` 打包）：
| 项 | 改前 | 改后 |
|---|---|---|
| 对局静止、省电开：每秒画几帧 | 30 | **15** |
| 同上：主线程占用 | 37% | **24%** |
| 同上：脚本占用 | 22% | **11%** |
| 同上：记进自动降画质的帧（每 5 秒） | 108 帧，平均 33.5 毫秒 | 0 帧（静止不计） |
| 静止中途碰屏 | — | 立刻恢复满帧 |
| 动画时间 / 真实时间 | 1.50 | 1.50（不变慢；1.5 是游戏速度设定） |
| 省电关（电脑） | 56 帧 | 56 帧（不受影响） |

**测试**：`rules engine jieqi bingfa beishui r6 bfai bfai.policy` 全过。P1、P2 两个补丁各自，以及先 P1 后 P2，在最新 `main` / `dev`（54ba8bc）上 `git apply --check` 都干净。

**建议（不在补丁里，TD 定）**：`?perf` 面板的“帧/秒”数的是浏览器的刷新次数，不是真正画了几帧，所以省电时还显示 60。Ham 用它看真机数字时会误判。可以改成显示 `Core.takeFrames` 或者真画的次数。

**上线说明（NEWS 草稿）**：手机上对局停着不动时更省电、更凉（优化部）。
