## 必须改（must-fix）

**M1　G1(c) 的探针在现行规则下会误报“封升级”。**
- 原因：破釜之后 `T.turn='r'`（`settle` 已经换手，bingfa.js:456）。`upgradeState` 要求走子方是这枚子的一方（bingfa.js:574），所以对任何楚子都返回 null。照原文写，`blocksUpgrade` 永远为真。
- 后果：现行规则下 C 凭空多出 2.5+0.3·军功（约 3～5 分），和 Code 量的 C≈0 正相反，等于让汉方“欢迎破釜”。
- 实测（probe_claims.js，第 41 题局面）：在 T 上把楚军功设成 99，没有一枚楚子升得了；把 turn 改成 b 以后就升得了。
- 方案 A 的被动封锁也会漏判：bfsim 是按 `S.turn==='b'` 判封锁期的（bfsim.js:105、113–120）。
- 修法：
  - 在 T 的副本上设 `turn='b'`、`upgraded=false`、`merit.b=99` 再探；
  - 再拿“同一局面把 fx.pf 清零”做对照，两者的差才是封锁的效果；
  - 结果按规则集缓存（每局或每个进程只探一次）。这样破釜已经用过、正在封锁期里的局面也有探针结果可用。

**M2　G1(c) 探针本身的开销。**
- think() 开始时 S0 轮到汉走，`pofuPairs(S0)` 直接返回空（bingfa.js:581）。要拿到一个破釜结果，就得在一个楚走的局面再完整枚举一次 pofuPairs。
- 这正是种子 21 第 16 步（4 万组合）、C37 刚压到 1.5 秒以内的那段开销，而且不在 pfCache 里。
- 修法：懒加载，直接用搜索第 1 层 pfList 已经算出来的组合；或者整局只探一次。

**M3　G1(a) 片段的搜索窗口会倒置。**
- 原文的子搜索窗口是 `(-beta, -max(alpha, need-0.01))`。当 `need-0.01 ≥ beta`（best 离 beta 不到 3.01）时 alpha > beta：子节点算完第一步就截断，返回的只是一个界，父节点可能把它当成“≥ need”的真值。
- 实测：种子 7002 的 11 个汉方局面里，630 次破釜子搜索有 **370 次（59%）** 窗口倒置。
- 修法：`lo=max(alpha,need-0.01); hi=max(beta,lo+0.01)`，子搜索窗口用 `(-hi,-lo)`，`v<need` 一律丢掉。原型就是这么写的，修好后全关时和 dev 完全相同。

**M4　G2 的触发门实际上不存在。**
- 原文条件是“回合 ≥ fromRound−1，或者差的那一功能由将军奖励凑出”。但 checkReward=1=G2_LOOK，后半句永远成立。结果是任何回合、只要有子“差 1 功”就开分支；兵、士、象在开局就常差 1 功。
- 照原文写的实测：
  - 42 个局面里 **20 个触发**，第 2～31 回合都有；
  - 触发的局面里第 3 层节点：中位 ×1.06、P90 ×1.82、**最大 ×2.64**（7002 第 6 步：29450→77738）；
  - CPU 时间 P90 ×1.73、最大 ×3.31；
  - 6/42 步着法改变。
- 说明里“种子 21 第 16 步 soon 为空”也不对：照原文那一步会触发。
- 只按回合门（第 15 回合起）时：
  - 8/42 触发；
  - 触发的局面节点中位 ×1.11、**P90 / 最大 ×1.54**（CPU ×1.91）；
  - 1/42 步着法改变；
  - **第 38 题能过（1/1）**，说明 G2 的机制是对的。
- 修法：
  - 删掉“将军奖励”那半句；
  - 另备减负选项：只在 `saving` 为真时开，或只开车炮马；
  - 代价按“触发局面的 P90 / 最坏”报，不要报“整步平均 +5～15%”。

**M5　G1(b)：多算 1 层过不了第 41 题，多算 2 层超闸。**
- 第 41 题实测：(b) 单开、(a)+(b)、(a) 单开都 ✗，根上分数和 dev 一模一样（1.59 / 1.03 / 0.89），`车2,3→8,3` 不在前四。
- 原因：破釜之后要走“汉安静一步 → 楚应 → 汉 `车→3,9` 不吃子的将军 → 楚被将死”。只多 1 层时，汉那步将军落在静态搜索里，而静态搜索只算吃子（bfai.js:141），看不到。
- 多 2 层时第 41 题能过（✓，+3.46），但代价是：
  - 汉方 23 个局面：节点中位 ×1.29、**P90 ×2.42、最大 ×2.71**；
  - 种子 21 三个最坏局面：×2.3～2.6（33181→75812 等）；
  - 只对第一个组合延伸，P90 也还有 ×1.91。
- 多 1 层本身：中位 ×1.09、P90 ×1.20、最大 ×1.46（CPU 最大 ×1.49），着法改变 0/42——**花了节点，没改棋**。
- 结论：说明里“41 ≥2/3（靠 b）”要撤。(b) 要么删掉，要么换成更便宜的办法（例如只在破釜线的静态搜索里加将军着法），再重新量。

## 应该改（should-fix）

**S1　G4 的深度前提读错了。**
- 现在楚方在根上核对破釜用 `d1=depthDone−1`、从第 1 层起搜（:434、:440）；普通着法也是 `d−1`、从第 1 层起搜（:396）——两者**本来就同深度**。
- G4 加 1 层以后，破釜线比它要比较的 bestV 深一层，而多出来的那一层是汉方应着。这种奇偶偏差会系统地压低破釜的分数，楚不分是不是陷阱都会少用破釜。
- 代价：楚方有破釜候选的 8 个局面，节点中位 ×1.10、最大 ×1.36。
  - 节点模式下，40% 的预算（校尉 2.4 万节点）更容易用满，能核对的候选变少；
  - 时间模式下，这一段会更常跑满 1 秒的上限（`max(400, 0.4·budget)`），所以楚方步的 P90 会涨。说明里的“最坏不变”只说了上限，没说 P90。
- 修法：同深度比较（bestV 那一步也加深重搜），或者只对将军着延伸。验收加第 25 题（G4 下实测仍 ✓）和楚方破釜使用率。

**S2　背水相关的事实错误。**
- `bfai_beishui.js` 改的是根上候选的静态预筛（dev :350 的 `gain≥4.5 → 2`，被将军时不设门槛），**没动 PF_MIN=5**，而且它是基于 b18c278 的。所以 `pofuMargin()` 到底共用哪个门槛，得先定下来。
- “楚车马炮比对方少”在引擎里是 `CFG.beishui.fewer[s]`（engine_beishui.js:24），不是 `beishui.on`。G1(c) 的兵法价条件化要读 `fewer[s]`，而且这等于在电脑里抄了一遍引擎规则（BF.ai v1 没有 artOpen 接口），说明里要写明。

**S3　G3 的覆盖面说过头了。**
- 刚解锁的主动技能当回合用不了：`promote()` 会给它们设冷却（bingfa.js:65，cooldownOnUnlock=1；`cdReady` 在 :130）。
- 实测：二级象升到三级后，“飞越吃子”不出现在 gen 里；同一局面换成原本就是三级的象，就有这一步。
- 所以“立刻有用”只看得到被动技能（践踏、禁卫、神速、回防）和“同一步结果变了”。说明里“天然覆盖飞越 / 齐射 / 踏营 / 霹雳 / 冲阵”不成立。这不影响第 39、40 题（两题都是被动）。可以把解锁判定直接限成“新增被动技能”。

**S4　G3 会改变新兵的走法。**
`useNow` 把候选标成 must，而新兵在 :328 挑的是 `x.must || x.gain>0.25`。说明写“校尉以下不动”，按原文实现会动。修法：判定加上 `L.depth>=2`。

**S5　G3 的“立刻有用”没有定义基线，触发频率也没量过。**
- 第 40 题这类“升级前这枚子一步也吃不到”的情况，`immediateGain` 拿什么当减数？原型里用的是 `max(升级前它最好的吃子后局面分, 当前局面分)`，要写进说明。
- Fable 的探针只数“新出现的着法”，不数“同一步结果变了”（践踏），所以“146 步里 0 次”不是这条判定的频率。
- 直接量的结果：
  - 42 个局面里判定只跑了 7 次，**命中 0 次**；
  - 节点和着法的影响 0/42；
  - 第 39、40、18 题各 1/1 通过。
- 所以 G3 在实战里几乎不出现，对打测不出来。验收改成“考题 + 同着法核对”，不要上 SPRT。

**S6　G1(c) 在现行规则下的技能权重和实测相反。**
- 说明给的权重是护驾 0.4～1.9、冲阵 0.3 等，而 Code 量的 46 个局面里 40 个 C=0。
- 封锁在搜索树里已经由引擎执行（`skillOk`，:134），视野内的部分搜索本来就看得见，再加静态项是重复计算。
- 修法：现行规则下默认 C=0，只在探到“封升级 / 封被动”时启用；权重用 Code 那 46 个局面标定（数据现成，便宜）。

**S7　6 万节点上限的尾部。**
- dev 把第 3 层算满已经要 P90 约 4.5 万节点，单个局面可达 9.3 万（7002 第 27 步就超了）。
- 任何 +20～50% 的尾部开销，都会让节点模式第 3 层算不完（:373–374），对打里悄悄变浅，和“变弱”分不开。
- 每个开关都要报“第 3 层节点”的 P90 / 最大，以及“没算满 3 层”的局面数，不能只报平均。

**S8　对打基线前后不一致。**
§1.6、2.6、3.6 写的是对 `git:b18c278`，§7 写的是对 dev。原型建在 dev 上，必须对 dev（或者上线的那一版），否则会混进 UPK / PFX 的差别。

**S9　验证方案太贵，信息量又低。**
- 按 §6 要跑约 8 组 SPRT（每组 600 局 × 6 万节点），再加方案 A 300 局和若干组 bfsim，在 4 核忙机上是几十 CPU 小时。而 SPRT[-30,10] 通过只说明“不明显变弱”，测不出说明预计的 ±10。
- 实测各开关的着法改变率：

|---|---|
| G3 | 0/42 |
| G2（只按回合门） | 1/42 |
| G1(a) | 1/42 |

- 建议：先用 `same_moves.js` 在固定种子上数“着法不同的步”，不同的那几步用霸王档深搜判对错；只有改变率达到几个百分点的（G1(a)、全开）才跑 SPRT。

**S10　bfsim 里的方案 A 和“第 16 回合起”都是用包装函数实现的。**
- `arts-from16` 预设下 `CFG.generalArts.fromRound` 仍然是 1（bfsim.js:83），所以 G1(c) 按 fromRound 做的兵法价条件化在这个预设下永远不会触发。
- 要测“第 16 回合起”，用 `--set generalArts.fromRound=16`，或者在说明里写明这一点。

## 附注（note）

- **G2 实现细节：**
  - ab() 里没有“只算某一枚子的着法”的入口（UPK 的 own / off 只在根上，:385–391）。原型里用了一个 `T.g2only` 标记；`cloneState` 不复制它，所以子节点不受影响。
  - 根上给候选排序时那枚子还升不起，`upgradeState` 返回 null，要临时把军功垫够再算。
  - G2 只在第 2 层、只为一枚子开分支，会让电脑略偏向“当场来钱”的着法：将军 +1、吃子，甚至被吃也有 +1 补偿。对打时看一下 bfsim 里的将军次数。
- **G1(a) 的其他细节：**
  - `best` 里含了“先升级再应”的分支值。在升级分支的内层调用里 alpha 已经抬高，普通着法可能 fail-low，best 只是上界，need 偏大，少数破釜线会被错丢。误差有界。
  - margin=3 时：节点合计约 −1%～−7%，最大 +8%；着法改变约 1/21 个汉方局面。
- **说明里两个数不能直接比：**“56% 怕破釜”是静态 q≥3 的组合比例，“楚 0 次用”只来自 3 局（3 局都是楚胜）。
- **G3 里的 TIMEOUT：** `upgradeCands` 里加的 `if (now()>deadline) throw TIMEOUT` 要删掉。那时 deadline 还是 Infinity（:321），而 :326 外面没有 try，真抛出来会把 think() 打崩。
- **G1(b) 和将军延伸共用 CX：** 破釜后的反击本来就是将军链，先用掉一次延伸，后面就少一次。另外第 31～35 题都是破釜已用的局面，(a)(b) 不触发，测不了它们；只有 (c) 会影响这几题。
- **背水：** `fx.pf=cnt.b+1`，楚走完就归 0，所以“C=0”的推论成立；汉方第 1 层枚举时，背水条件不满足会提前返回，代价不变。
