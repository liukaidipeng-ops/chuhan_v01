## 第 3 问：执汉 44% 对执楚 77%，差距从哪来，总胜率怎么读

### 结论
1. 这 33 个百分点的差距，**约 28～33 个百分点是游戏本身的不对称**，剩下的是噪声。新版两种颜色**都**比旧版强，强的幅度两边差不多。
2. 60.7% / Elo +76 应读作"**换边各半、颜色抵消后的平均强弱差**"。它是公平的，但因为提前停偏乐观，诚实的说法是"+10～+147 的区间里，最可能 +50～+80"。
3. 不需要复杂的"带颜色项的 logistic 模型"：换边设计下它恰好等于下面这个加减法。**建议工具直接打印这两个数**（强弱 d、颜色 c），再加一条"两种颜色都不退步"的检查。

### 证据和算术【已核实，`q3q4_calc.js`】

**H15 的原始数字**（chat-to-code.md H15 行 126–127）：新版执汉 24/54、执楚 41/53，共 65/107 = 60.7%，无和局。反过来：旧版执汉 12/53 = 22.6%，旧版执楚 30/54 = 55.6%。

**第一步：把每种颜色换成 Elo**（公式 Elo = −400·log10(1/p − 1)，即 bfsim.js:535 的 `eloOf`）
- 新版执汉 44.4% → −38.8 Elo
- 新版执楚 77.4% → +213.4 Elo
- 合并 60.7% → +75.9 Elo（和 chat 报的 +76 一致）

**第二步：拆成"强弱"和"颜色"两项**（2×2 换边设计下这就是带颜色项的 logistic 模型的精确解）
- 强弱 d = (执楚 Elo + 执汉 Elo) / 2 = (213.4 − 38.8) / 2 = **+87.3 Elo**
- 颜色 c = (执楚 Elo − 执汉 Elo) / 2 = (213.4 + 38.8) / 2 = **+126.1 Elo（楚方占优）**
- 两者的标准误都约 ±38 Elo（每种颜色只有 53～54 局：执汉 ±6.8 个百分点 ≈ ±48 Elo，执楚 ±5.7 ≈ ±58 Elo）。

**第三步：和游戏本身的不对称对照**
- 等强电脑自对弈汉 36%（NOTES 1.1，9ff64a4 现行规则；旧电脑也 35%）→ 颜色项 = −100 Elo，即楚 +100。对打里估出的 c = +126 ± 38，和 100 在误差内一致。
- **预测**：如果新版两种颜色一样强 +76 Elo、颜色差按基线 100 Elo，预期执汉 = σ(76 − 100) = **46.5%**，执楚 = σ(76 + 100) = **73.3%**；用 d = 87 算是 48.2% / 74.6%。实测 44.4% / 77.4%。预测的差距 27～28 个百分点，实测 33，差的 5 个点在噪声之内。

**第四步：按颜色各自对基线的提升**
| | 执汉 | 执楚 |
|---|---|---|
| 基线（等强） | 36% | 64% |
| 新版 | 44.4%（**+8.4**） | 77.4%（**+13.4**） |
| 旧版 | 22.6%（−13.4） | 55.6%（−8.4） |
| 新版超过基线的 Elo | +61 | +114 |

两种颜色的提升差 53 Elo，但合并标准误约 75 Elo，只有 0.7 个标准差——**不能说新版的进步偏向楚方**。（算术上两行必然对称：新执汉比基线多出来的，正好等于旧执楚比基线少的。）

**第五步：方差里有一块是"颜色分裂"**
单局方差 0.2384 = 颜色内方差 0.2110 + 颜色分裂 0.0271（占 11.4%）。换边设计已经把颜色平衡掉了，所以工具按单局方差算的区间略偏宽：工具 51.5–70.0%（Elo +10～+147）；按颜色分层算 52.0–69.5%（+14～+143）。差别小，但说明配对 / 分层方差更准（第 4 问详谈）。

**附带观察**【推断】：两个不同版本对打时，汉方总胜率比自对弈低——H8 28%、H14 32%、H15 34%、本机 9ff 变体对 9ff 26%，而自对弈 36%。可能原因：新版执楚更会抓旧版汉方的漏洞（H8 行 347：新版执楚 118/144 局在第 11 回合用破釜，旧版执楚只 49/145 局、第 19 回合）。所以**颜色项要从对打本身估（c），不要直接拿 36% 去减**；b18c278 自对弈现行规则的数还在跑（NOTES P0 第 3 条），出来后可以再对一次。

### 建议
- **建议改**：bfsim 对打汇总里加两行：`强弱 d = … Elo（执汉 … / 执楚 …）`、`颜色 c = … Elo`，并打印"新执汉 vs 旧执汉、新执楚 vs 旧执楚"的对比。门槛里加一条诊断：**两种颜色都不能比旧版同色差**（H8：31% vs 25%、75% vs 69% ✓；H15：44% vs 23%、77% vs 56% ✓）。防的是"只学会一边"的版本。
- **建议改**：`bfai-qualification.md` 行 53 把"区间整个在 0 以上（明显更强）"改成"换边后 60.7%，Elo 约 +50～+80（提前停，点估计偏乐观）；执汉 / 执楚都比旧版强"。
- **没问题**：用总胜率 60.7% 作为强弱的主指标是对的，换边设计已经抵消颜色。不要改成"按颜色对基线"当闸门（基线随电脑版本变 6～10 个百分点，NOTES 1.1）。

## 第 4 问："只对上一版、固定种子"够不够证明"更强"？LLR 阈值和局数上限

### 结论
- **不够证明"更强"，够证明"不比旧版弱"**——这正是检验设计的本意，问题出在怎么读结果。
- 统计上（α/β、界、提前停）**没问题**；工程上有两处**必须改**（种子、结论措辞 + 上线前确认），四处**建议改**（配对方差、锚点对手、"没结论"的处理、霸王档抽查）。

### 证据，逐项

**(1) 检验的实现**【已核实】bfsim.js:536–546
- 每局新版得分 1/0.5/0（行 537），均值 m、单局方差 v（538）。
- LLR = (s1−s0)·(2mn − n(s0+s1)) / (2v)（543），s0 = σ(−30) = 0.4569，s1 = σ(+10) = 0.5144，中点 0.4857（= −10 Elo）。这是 cutechess 同款的"用样本方差的 GSPRT"。
- 界 = ln(0.95/0.05) = ±2.944（544），α = β = 0.05。每下完 2 局检一次（582），越界就不再派新局（正在下的下完）。
- 我复算：64/106 → LLR 3.01（H15 报 3.01 ✓）；70/120 → 2.77（H14 报 2.77 ✓）。

**(2) `[-30, 10]` 的含义**【已核实，`sprt_sim.js` 用工具的原公式精确模拟 2 万次，上限 600 局】

| 真实差距 | 通过 | 不通过 | 600 局没结论 | 平均局数 |
|---|---|---|---|---|
| −30 Elo（真弱） | **4.0%** | 76.1% | 19.9% | 347 |
| −10 Elo | 28.4% | 28.7% | 42.9% | 437 |
| 0 Elo（一样强） | 51.7% | 12.2% | 36.0% | 414 |
| +10 Elo | 75.6% | 4.2% | 20.1% | 351 |
| +35 Elo | 99.0% | 0.3% | 0.7% | 196 |
| +76 Elo | 100% | 0 | 0 | 99 |

读法：**"通过" ≈ "真值大概率不低于 −10 Elo"**。一个和旧版一模一样强的版本也有 52% 的机会通过。所以通过 ≠ 更强。工具注释写得很明白（bfsim.js:25–26："想证明'更强'用 --sprt 0,40"），但 H15 和合格标准文档都把它写成了"明显更强"。H15 的 106 局提前停和 +76 本身是对的——以 +76 的真值，平均 99 局就该越界。

**(3) α/β 与小样本提前停**【已核实】
- 误通过 4%、误否 4%，接近名义 5%。每 2 局检一次没有把错误率抬起来。
- 小样本确实可能提前停：12 局 11 胜、16 局 14 胜、20 局 17 胜、30 局 24 胜就会判通过。但一样强的版本在 30 局内误通过只有 0.6%；加"最少 40 局再检"对错误率和平均局数几乎没影响（−30 Elo：347 → 351 局）。**第 5 问的复跑恰好就是 16 局 14 胜提前停**，所以这不是纸上谈兵。
- **提前停的点估计偏乐观**（赢家诅咒）：真值 +35 时，通过那些次的平均报告值是 +54；真值 +56 → 报 +75 左右；真值 +76 → 报 +98。**偏高约 20 Elo**。H15 的 +76 按此折算真值约 +55～+60，和 H14 独立的一组（对 a2cf15c 58.3%）、链式相加（d492bfa +20 再 +58 ≈ +78）大致吻合【推断】。
- 工具打印的"95% 区间"是按固定样本算的，提前停之后它不是真的 95%，H15 的"+10～+147"下界偏高。

**(4) 种子：每轮都是 1**【已核实】
- bfsim.js:319 默认 `seed: 1`；行 561 第 i 对用 seed+i；行 378 每局 `Math.random = mulberry32(seed·2654435761)`；两版电脑校尉档 `noise: 0.3`（b18c278 行 226 / 25eb911 行 178），行 375、382 全程用 `Math.random` 挑着——**同一种子、同一对版本、按节点收手，整局完全可复现**，重跑同一条命令零新信息。
- bfai_gate.js:57 只在用户给 `--seed` 时才传；chat 三轮总闸命令都是 `node tools/bfai_gate.js --quick`（chat-to-code.md 行 139、339、369）→ H8、H15 都在种子 1…300 上打，25eb911 每次执同色时拿到同一条随机数流。
- 后果：(a) 300 个种子是开发者看得见、可反复试的固定集合，和考卷一样会被"应试"（不一定故意：chat 每改一处就对这批局面打一次，选留下的改动天然偏向这批种子）；(b) 两轮之间不独立，不能把 H8 和 H15 当两份证据相加。
- 开局随机化本身**没问题**：前 6 步按 `open` 档（校尉 + noise 0.9、30% 概率在前 3 里挑，bfsim.js:445、507），之后校尉档的 noise 0.3 继续随机，局面多样性够。

**(5) 配对（五项式）方差 vs 单局方差**【已核实，`pento.js` 跑本机 5 份对打明细】

| 对打 | 局数 | 配对里 1:1 分的占比 | 配对 SE / 单局 SE | LLR 单局 → 配对 |
|---|---|---|---|---|
| hoard 对 9ff | 277 | 85/138 | **0.87** | −2.21 → −2.77 |
| rooklater 对 9ff | 181 | 55/90 | **0.86** | −2.21 → −3.15 |
| limitup 对 9ff | 300 | 131/150 | **0.50** | −0.62 → −2.49 |
| pawnfirst 对 9ff | 27 | 5/13 | 0.84 | −2.36 → −3.70 |
| 本次复跑 b18c278 对 25eb911 | 17 | 2/8 | 0.83 | 2.27 → 3.82 |

这个游戏颜色效应大（同一种子两局常常"谁执楚谁赢"），所以配对方差明显小于单局方差，**现在的检验比必要的慢 15～50%**。limitup 那组按单局方差 300 局没结论，按配对已经接近"不通过"。实现时要注意：全部 1:1 时配对方差为 0，要加下限（如 max(v, 0.02)），9ff 自对自的测试文件里就出现了方差 0。另外行 582 按"完成的局数是偶数"检，不按种子配对——多进程时完成顺序乱，检验那一刻颜色可能不平衡（H15 停在 106 局时正好 54 : 52）。影响小，但改成"按完整配对检"顺手。

**(6) 非传递与链式漂移**【已核实的事实 + 推断】
- cf47f5e 考卷满分、对 bee5741 −105 Elo（H3 行 413；bfai-qualification.md 行 24）：考卷不是强弱指标，对打才是——这点大家已经接受。
- 对打链：bee5741 ≈ 25eb911 → d492bfa（+20，H8）→ b18c278（+76 对 25eb911；+58 对 a2cf15c，H14）。链是自洽的。
- 风险在于"赢上一版"可能靠**抓上一版的特定漏洞**：H8 行 347，新版执楚第 11 回合就破釜、118/144 局，因为旧版汉方不提防；一旦下一版汉方学会提防（9ff 加过 `pfPly`），这部分优势就消失，但对人下棋未必是真提升。**只对上一版打，这种"专克上一版"的改动会一路通过**。
- 旧版电脑用 `git:提交号` 随时能拉（bfai-qualification.md 行 67–71），加锚点对手几乎没有工程成本。

**(7) 600 局上限与"还没有结论"**【已核实】bfai_gate.js:59：只有打印出"通过"才算合格，"还没有结论"记为不合格。一样强的版本 36% 会到上限（上表）。这是保守的，但它把"等强"和"变弱"混在一起，而且结果取决于上限多大，不是原则性的判定。

**(8) 只测校尉档**【已核实】bfai_gate.js:57 不传 `--level`，bfsim.js:319 默认 `mid`；`hard=200000` 在对打里根本没用上。霸王档的强弱（深度 7、q=4，和校尉 3 层差很多）**从来没对打过**。如果用户主要和霸王档下，总闸测的不是他看到的那个电脑。

### 建议（具体设置）

**必须改**
1. **每轮换种子，并写进报告**：`bfai_gate.js` 默认 `--seed` 改成当天日期（如 20261004）或 `bfai_gate.json` 里一个自增计数，总闸输出和 `--match-json` 里都记种子；留一段**保留种子**（如 9001–9100）只在上线前确认用，平时不碰。理由：见 (4)；成本为零。
2. **措辞和上线流程**：总闸的"通过"一律写成"不比旧版明显弱（真值大概率 ≥ −10 Elo）"；要在文档 / 报告里写"更强"，须另跑**新种子、固定 200 局**（`--sprt 0,0`，见第 5 问）：点估计 ≥ 55% 且区间下界 > 50% 才写"明显更强"。理由：(2)(3)，提前停的点估计偏乐观 20 Elo，H15 的区间不是真 95%。

**建议改**
3. **配对方差 + 最少 40 局再检 + 按完整配对检**（bfsim.js:536–546、582）：省 15～50% 局数，顺带消掉 16 局提前停这种尴尬；错误率不变。方差加下限。
4. **锚点对手**：除对线上版 SPRT 外，每次过闸再对 `git:25eb911`（将来线上换了也不换锚点）打固定 100 局、新种子，只记录累计 Elo，不设门槛；要求累计 Elo 不下降。理由：(6)。每轮多约 1 小时（chat 机器 80 局 24 分钟）。
5. **"还没有结论"改成"待定"并打印区间**，由人决定；上限 600 保持（真值 0 时平均 414 局，已经够长）。理由：(7)。
6. **霸王档抽查**：过闸时加 40 局 `--level hard`（`--nodes hard=200000`），只量基准、不设门槛，先看校尉档的结论在霸王档是否同向。理由：(8)。

**没问题**
- 界 `[-30, 10]`、α = β = 0.05、±2.944、每 2 局检一次、第 106 局提前停：错误率接近名义值（表 (2)），不必改界。备选方案我也算了：`[0, 40]` 一样强时通过 5%、+35 时 90%、但平均要 400～480 局，作为"更强"的专用检验可以，不适合当日常闸门；`[-20, 20]` 一样强时通过 50%、平均 656 局，更慢，没有好处。
- 开局随机化（6 步）和全程 noise 0.3：多样性够，不是 300 个固定开局。
- Elo 换算与 95% 区间的算法：我复算 +75.9（+10.4～+147.2），和工具一致。
- 和局按 0.5 处理（本局没有和棋，只有回合上限 / 卡死算和），没问题。
