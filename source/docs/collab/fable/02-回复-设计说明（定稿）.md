## 1. G3 · 士 / 象（规则无关，先做）

### 1.1 问题是什么

**【已核实】升级候选怎么被砍的**（`bfai.js:287–314`，`upgradeCands()`）：
- `:305`：`must` = 大子 / 守子正被捉（`threatened`）、或正被将军；
- `:308`：`if (defender && !must && !(p.t === 'a' && heavy && p.lv < 2)) continue;`——**没被捉的士象一律不进候选**，唯一例外是“对方两血进攻子逼近时士一升二”；
- `:309`：攒车钱 / 攒终极时非车不升；`:313`：`cand.slice(0, 3)`。

我在 dev 上跑 3 局自对弈（3000 节点，146 步），把每步的全部升级候选按“被哪条砍掉”分类：守子候选被 `:308` 砍 **430** 个、被 `:313` 砍 5 个、留下 37 个（31 个是 `must`）。**所以 NOTES 1.5 的“只留前三名把守子挤掉了”诊断错了**：象根本没进那张表。

**【已核实】考题 39、40 在 dev 上**：
- 39 升象践踏：象 3→4 花 5 功，静态 gain = −0.53，没被捉 → `:308` 砍掉。升完之后这枚象立刻能走的 `(4,7)→(6,5)` 吃兵触发践踏，连杀 5 子，局面分 +15.2（升之前同一步 −7.76）。电脑选了升车出车（−3.52）。
- 40 升士禁卫斩车：士 3→4 花 4 功，gain = −0.30，没被捉（楚车攻击 1 打不死 3 血士）→ 砍掉。升完立刻 `(4,1)→(4,2)` 斩车 +7.32。电脑选了升车吃车（−1.28）。
- 评审原型把 `:308` 放开后两题都 ✓（两边评审各自复现）。

**【已核实】这是不是个真缺口（H24 的 300 局）**：汉 a2 75.3% 的局升过、a3 42.3%、e2 50.0%；楚 a2 58.7%、e2 40%。**士象升得并不少**，只是全是 `must`。少的是技能级（a4 10.7%、e3 11%、e4 0.7%）；现行价目下这本来就不划算（象升到四级共 10 功，估值只给 +0.4/+0.9，`:32`），Code 的军功实验（极限升级 −16、攒军功 −34）也说别乱改升级意愿。

**【已核实·评审补的两条】**
- `cooldownOnUnlock: 1`（`bingfa.js:21`；`promote()` `:65` 给刚解锁的主动技能设冷却）：炮 / 车 / 马 / 相 二升三之后，当回合可用的技能着法是 0（评审 `probe_claims.js`、`probe_checks.js` 都验了）。所以“升完立刻有用”**只有被动技能**（践踏、铁甲禁卫、神速营、回防）和血量 / 攻击力的变化——霹雳、冲阵、飞越、齐射、踏营都不会出现。39、40 正好都是被动。
- 真实触发频率：评审用修正后的公式量 320 步，触发 1 次（士三升四铁甲禁卫，真的）；42 个局面上判定跑了 7 次、命中 0 次。我草稿里“146 步 0 次”是比着法字符串数的，看不见“同一步升级后结果不同”的践踏型机会，不能当证据——结论“稀少、一出现就是整局”仍对，证据换成评审的。

结论：**G3 是真缺口，但很窄、只在被动本事上；修这一条，别碰宽的。**

### 1.2 方案（`BFAI_G3`，默认 1）

挂在 `upgradeCands()` 的循环里（`:305–310`），在 `:308` 之前加一条判定：

```
// G3：守子升一级多出一项被动本事（铁甲禁卫 / 践踏……），而且升完这一手它自己就能多打到子——当保命升级看待。新兵档不走这条
let useNow = false;
if (G3 && defender && !must && L.depth >= 2 && newPassive(p)) {
  const sT = score(T, me);
  const b0 = Math.max(bestOwn(S, p.id), base), b1 = bestOwn(T, p.id);
  useNow = b1 > -INF && (b1 - sT) - (b0 - base) >= G3_MIN;      // 默认 1.5
}
if (defender && !must && !useNow && !(…原来的士一升二例外…)) continue;
if ((saving || hoard) && p.t !== 'r' && !must && !useNow) continue;   // useNow 只在守子上为真，车炮马不绕开攒车钱
cand.push({ …, must: must || useNow });
```

- `newPassive(p)`：`BF.levelInfo(p.t, p.s, p.lv + 1).skills` 比 `levelInfo(…, p.lv).skills` 多出的技能里，有 `CFG.skills[k].passive` 为真的。`levelInfo` 在 `bingfa.js:854`，已导出。现行规则下只有士 3→4（禁卫）、象 3→4（践踏）、兵 3→4（神速 / 回防；兵不是守子，不走这条）会为真。
- `bestOwn(X, id)`：枚举 `A.gen(X, true)` 里 `it.p.id === id` 的吃子 / 技能着法，各 `BF.attempt` 一次、`score()` 打分，取最大；没有则 −INF。
- **公式是相对差**：升级后“它最好的一手比升级后的局面好多少”减去升级前同样的量。评审原型用绝对差（`b1 − b0`）时 320 步触发 15 次、14 次是车炮马二升三的假触发（差值正好等于升级本身的 +1.6～+4 分）；改成相对差只触发 1 次、是真的，39、40 仍 ✓、18 仍 ✓。
- `useNow` 只给守子；车炮马不绕开 `saving / hoard`（评审量到绕开会让炮、马抢车的钱）。
- `L.depth >= 2`：新兵档 `:328` 挑的是 `x.must || x.gain > 0.25`，不加这条新兵也会升——草稿说“校尉以下不动”，按原文实现会动，现在真不动了。
- `:313` 的 `slice(0, 3)` 不改（`must` 排前面，三名够用）；`:425–427` 守子升法要比不升好 0.4 才选，不改（39/40 差十几分，0.4 拦不住，平时正好防乱升）。
- **不加** `throw TIMEOUT`：`upgradeCands` 在 `:326` 调用时 `deadline` 还是 `Infinity`（`:321`），外面也没有 try，真抛出来会把 `think()` 打崩。这段本来就 <1 ms，不需要。

**子开关 `BFAI_G3B`（默认 0，只供模拟）**：评审指出 `:308` 本身就是一条写死的“守子平时不升”规则，设计者在测的守子规则（士反击近战、四级技能降到三级）在模拟里会因此显得“还是没人升”。G3B=1 时，候选里没有守子就把静态分最好的 1 个守子升级作为第 4 个候选加进根节点，靠 `:427` 的 0.4 门槛和第 18 题防乱升。线上默认关：这是没量过的升级意愿改动，Code 的实验说这类改动一般是负的；Code 测 ctr-* 预设时可以开。

### 1.3 怎么从 CFG 读规则

全部走 `BF.levelInfo` / `CFG.skills[k].passive` / `BF.ai.gen` / `BF.attempt`：哪一级解锁什么、是不是被动、践踏踩到谁，都是引擎说了算。改价目只影响 `upCost`→`upgradeState`；“四级技能降到三级”、被动改主动（那它就不再算“升完立刻能用”，正确）、新增被动都自动跟。背水 / 方案 A 与它无关。

### 1.4 预计效果

- 考题：39、40 校尉 3/3（评审原型各 1/1、3/3）；18 保持 3/3（`useNow` 要求“立刻多打到子”，18 题没有）。
- 实战：触发 ≈0.3% 的步，对打**测不出来**（评审两边都这么判）。bfsim 的 a4/e4 行在 ±5 个百分点噪声里，不拿它验收；改成按触发记数（§1.6）。
- 对打：0 ±测不出【已核实：42 局面着法 0 变】。

### 1.5 风险和代价

- 判定只在守子差一级到被动级时跑（42 个局面 7 次），每次 ≤8 个 `attempt` ≈ 0.2 ms；节点 0 变（根上多 1 个候选的情况 320 步里 1 次）。最坏局面不涉及。时间模式无影响。
- 会错的局面：相对差只看一手静态分，可能被“升完吃一个、下一步被反吃”骗进候选——但进的是根节点搜索，三层会把它比下去，只花节点不改着法。

### 1.6 怎么验证

1. `bfai_exam.js --only 战略`：39、40 要 3/3；`--only 军功`（含 18）、`--only 技能` 不退。
2. `same_moves.js` 固定种子：G3 开 / 关着法逐步比对，不同的步用霸王档深搜判对错（预计 0～2 步不同）。
3. 按触发记数（评审建议）：判定跑了几次、命中几次、命中后被选中几次、选中后 3 步内的局面分变化。**有效** = 考题过 + 不同的步深搜不判坏；**失败收回** = 18 退步，或 r2/r3 首次升到的回合推迟 >1。
4. **不上 SPRT**（测不出，白花几十 CPU 小时）。
5. `BFAI_G3=0` 时着法逐一同 dev。

**白话（给设计者）**：电脑原来有个死规矩“士和象没被人捉住就不花钱升级”。改完以后只有一种情况它会破例：升这一级马上多出一项**被动**本事、而且这一手就有收成——四级士能直走一格，正好一刀砍死钻进九宫的两血车；四级象踩着过河兵，把挤在河边的车马炮一圈踩死。注意：只对升完立刻生效的被动本事（践踏、铁甲禁卫）有用；新解锁的主动技能（霹雳、冲阵、飞越……）按规则要等一回合才能用，所以“升炮立刻放霹雳”这种它不会、也不该算。平时它还是不会给士象乱花钱。

## 2. G4 · 楚方拒饵（第二做；原来排最后，评审证明它独立、便宜、有效）

### 2.1 问题是什么

**【已核实】楚方根上怎么核对破釜**（`:433–447`）：破釜候选先按静态 `gain ≥ 4.5` 预筛留 8 个（`:350`），再用 `-ab(k.S, d1, -INF, -need + 0.01, 1)` 核对，`d1 = depthDone − 1`，`need = bestV + PF_MIN(5)`，预算 40%（节点模式 `nodeCap`，时间模式 `deadline = now + max(400, 0.4·budget)`，`:436`）。
**我草稿说它“不加延伸、比普通着法浅”——错了**：普通根着法也是 `d − 1`、从第 1 层起搜（`:396`），两者本来同深度。真正的问题是 41 题的陷阱要在破釜之后再看“汉安静一步 → 楚应 → 汉不吃子的贴脸将军 → 将死”，比核对深度多 2 层；而静态搜索只算吃子（`:141`），不吃子的将军看不见。
**【已核实】**评审 `q41_chu.js`：41 题汉方下饵（`车2,3→8,3`）之后，dev 楚 3/3 咬饵（破釜吃车）；核对多算 1 层的楚 3/3 拒饵；25 题（破釜白杀一车）仍 ✓。

### 2.2 方案（`BFAI_G4`，默认 1）

- `:440`：`-ab(k.S, d1 + (G4 ? 2 : 0), -INF, -need + 0.01, 1)`。**多 2 层而不是 1 层**：多 1 层时破釜线比它要比的 `bestV` 深一层、而多出的那层是汉方应着，奇偶偏差会系统性压低破釜分数（评审指出），楚不分陷不陷阱都会少用破釜；多 2 层落在同一方，不偏。预算仍是 `:436` 的 40%，节点模式用满就按原深度结果、核对不完的候选是弱的（`:438` 按 `gain` 排序先算最狠的）。
- 背水：预筛 `gain ≥ (CFG.beishui && CFG.beishui.on ? 2 : 4.5)`，楚被将军时不设门槛——这是 Code 的 `bfai_beishui.js` 已经在模拟里用的，并进正式电脑。**`PF_MIN = 5` 不动**（草稿说 `bfai_beishui.js` 改了 PF_MIN，错了，它改的是预筛）。
- 不做“主动下饵”的额外启发（那是 G1 的事）。

### 2.3 CFG

`CFG.beishui.on` 决定预筛门槛；“第 16 回合起”由 `pofuPairs` 在 `artOpen` 前返回空自动处理（`bingfa.js:581`）；破釜改成别的一次性兵法时核对逻辑不变。

### 2.4 预计效果

- 考题：25 ✓（评审 +1 层实测 ✓；+2 层只会看得更清）；41 的“楚方拒饵”反题（Code 要补，§7）应过。
- bfsim：“楚破釜 N 局，胜 x%”那行胜率略升、局数略降【推断】；**失败** = 楚方破釜使用率掉到 30% 以下（变得不敢用）。
- 对打楚方 0～+10【推断】；42 个局面着法 0 变（+1 层）。

### 2.5 风险和代价

- 评审实测（+1 层）：楚方有破釜候选的 8 个局面节点中位 ×1.10、最大 ×1.36。+2 层更贵，但有 40% 上限兜底：节点模式最坏 ×1.4；时间模式这段更常跑满 `max(400, 0.4·budget)`，**楚方步的 P90 会涨**（草稿说“最坏不变”只说了上限，没说 P90——评审对）。要量楚方步的 P90（§2.6）。
- 若 +2 层让楚方步 P90 超过第 6 道闸：退到“只对 `gain` 前 2 名多 2 层，其余原深度”，再量。不退到 +1 层（有奇偶偏差）。

### 2.6 怎么验证

## 3. G2 · 军功规划（规则无关，第三做）

### 3.1 问题是什么

**【已核实】“电脑不知道进账”只对一半**：
- 进账是引擎在 `attempt → endTurn` 里发的（`bingfa.js:457–459`：楚方走完、`round(S) >= autoIncomeFromRound` 时两边各 +1）。搜索树里每过一个楚方回合，军功就已经加上了——电脑**看得见钱到账**。
- 看不见的是**己方下一回合的升级**：`:332 upPly = 1` 只在第 1 层给**对方**开“先升级再走”（`:186–204`），己方升级只在根上（`:326`）。所以“这回合别花、下回合进账正好升三级车绝杀”（38 题）这条线在树里不存在：dev 选 `车4,4→8,4×炮 10.6`，标准答案 `车4,4→4,7` 没进前四。
- 上限 30 几乎碰不到：6 份 300～400 局的 JSON 里军功 ≥28 的采样点 0.4%～2%；3 局自对弈里“贴上限浪费”= 0。“贴上限”这一项只为规则改了（军功涨价、回合拉长）以后不出事。
- 已有的 `saving`（`:294–296`）在 38 题已生效，电脑没乱花钱，它错在把车调走。**G2 的核心是搜索，不是估值。**
- 触发频率：3 局里第 15 回合起的 62 **步**（半回合，不是草稿写的“回合”）中 36 步存在“某枚子的升级价 ∈ (军功, 军功+1]”——不稀少，所以分支必须收得很窄。

### 3.2 方案（`BFAI_G2`，默认 1）

**(a) 搜索：第 2 层给己方开 1 个“刚够钱”的升级分支**

根上（`think()`，`:332` 之后）：
```
g2Soon = null;
if (G2 && L.depth >= 3 && round(S) >= CFG.merit.autoIncomeFromRound - 1) {
  const LOOK = CFG.merit.autoIncomePerRound, m = S.merit[me]; let bestG = -INF;
  for 每枚己方子 p（不含帅将；士象不含，决战除外）{
    const c = A.upCost(p); if (c == null || c <= m || c > m + LOOK) continue;
    const X = clone(S); X.merit[me] = c; X.upgraded = false;        // 根上它还升不起，临时垫够钱才算得出静态分
    const T = A.upgradeState(X, at); if (!T) continue;
    const g = score(T, me) - base; if (g > bestG) { bestG = g; g2Soon = p.id; }
  }
}
```
`ab()` 里，普通着法循环之前：
```
if (G2 && ply === 2 && side === rootSide && g2Soon != null && !S.upgraded) {
  按 id 找到那枚子的位置 at；const T = A.upgradeState(S, at);        // 用树里的真实军功：钱真到了才非空
  if (T) for (const it of order(A.gen(T, false).filter(x => x.p && x.p.id === g2Soon)))
    { 和普通着法一样 attempt / -ab(r.S, depth - 1, …) / 更新 best、alpha，截断就 return }
}
```
- 只接着算升的那枚子自己的着法（38 题正是“升车→车吃马将军”）；在本节点里直接循环那枚子的着法，不需要给状态加标记（`cloneState` 不会复制自定义字段，评审提醒的坑这样就避开了）。
- **触发门只按回合**：`round(S0) >= autoIncomeFromRound − 1`。草稿里“或者差的那一功能由将军奖励凑出”这半句，因为 `checkReward = 1 = G2_LOOK`，永远成立，等于没有门——评审实测照原文写 42 个局面 20 个触发（第 2～31 回合都有）、最坏 ×2.64、着法 6/42 变；**删掉**。草稿说“种子 21 第 16 步不触发”也是按没门算错的，按回合门确实不触发（`w21p16` G2gate 节点 = dev）。
- 第 2 层之外不开；楚方根上破釜核对的子树里也适用。

**(b) 估值：贴上限的军功不值钱**（`:77`）：`usable(m) = min(m, cap − headroom)`，`headroom = 2 × autoIncomePerRound`（`round ≥ fromRound` 时，否则 0）；`v += 0.3 × (usable(me) − usable(opp))`。现行节奏几乎不触发，O(1)。

**减负子开关（默认关，Code 量了再定）**：`BFAI_G2_SAVING=1` 只在根上 `saving` 为真时开（那时电脑本来就在等这笔钱）；或只开车炮马（现在守子已排除）。
**不做**：改 `saving`（Code 实验：不急着升车 −46、攒军功 −34）、改 0.3 斜率、极限升级（−16）。**也不做**评审建议的“按树里实际军功（含杀子进账）判断是否开分支”：那等于去掉根上的窗口，代价回到“没门”的量级（P90 ×1.27、最坏 ×2.64），过不了第 6 道闸；留作以后的子开关。

### 3.3 怎么从 CFG 读规则

读 `CFG.merit.autoIncomeFromRound / autoIncomePerRound / cap`（`bingfa.js:15–19`）。进账时点不自己算，由 `attempt` 在树里发；即使改成每回合 2 功、或从第 1 回合起，第 2 层那个分支一样对（`upgradeState` 用的是树里的真实军功）。车升级涨价：`upCost` 变，`g2Soon` 自动变。`arts-from16` 这类 bfsim 预设是包装函数做的，不动 `CFG.merit`，和 G2 无关。

### 3.4 预计效果

- 考题：38 校尉 3/3（评审实测 1/1；根深 3：第 1 层楚应、第 2 层升车+吃马将军、第 3 层楚应将、被将军 `:180` 再往下一步 → 杀）。38 的对照（第 10 回合）照样吃炮（回合门不开）。
- 实战：触发 8/42 个局面、着法 1/42 变【已核实】。bfsim 的“首次升到 3 级”那行在 ±5 个百分点噪声里，不拿它验收；改成按触发记数。
- 对打 ±10 以内【推断】。

### 3.5 风险和代价

- **已核实**（评审原型，回合门）：触发局面第 3 层节点中位 ×1.11、P90 / 最大 ×1.54，CPU 最大 ×1.91；不触发的局面 0 变。按“触发局面的 P90 / 最坏”报，不报“整步平均”。

- 最坏局面（种子 21 第 16/18/20 步，第 9～11 回合）：回合门不开。时间模式都在 `ab()` 里受时限。

### 3.6 怎么验证

## 4. G1 · 封锁期的账（依赖规则，最后做；三个子开关分别测）

### 4.1 问题是什么

**【已核实】现在的汉方电脑怎么看破釜**：
- `:333`：楚的破釜没用，`pfPly = 1`——第 1 层（楚的应着）里加破釜组合。`:162–171` / `:230–231`：组合先按静态 `q ≥ 3` 筛、留最狠 4 个；`:238` 破釜之后那条线深度 `depth − 1`（和普通应着一样）。破釜之后 `used.art.b = 1`，估值 `:80` 的兵法价 3 分自动掉。
- 楚方自己（`:433–447`）：静态 `gain ≥ 4.5` 预筛，搜索值要比最好的普通走法高出 `PF_MIN = 5` 才用。

**不对称**：汉方把“楚破釜后比普通应着高一点”的组合都当真；楚方自己要高出 5 分（加上估值已扣的 3 分兵法价，静态要赚 8 分上下）才用。
**证据要换**：草稿用“汉方走子后 56% 的局面有 q≥3 的破釜组合、楚实际用 0 次”证明“防过头”——评审指出这个数读反了：56% 是汉方走完**还留在棋盘上**的威胁（没躲的），不是“怕过的”；0 次只来自 3 局。该量的是“把破釜提防关掉，汉方着法变不变”：评审在 25 个汉方局面上量，**8 个变了（32%）**，其中 3 个关掉提防后走的那步会留下 q≈9～13 的破釜——这么大的，门槛 5 的楚方也会用，这几次躲是对的。所以“防过头”是真的，但比草稿说的小；G1(a)（门槛 3）只改了 1/42（评审 2）或 4/25（评审 1）步，破釜暴露量没变。

**封锁期的账在哪里才值钱**：现行规则下 Code 量的 C 46 个局面 40 个 = 0；方案 A（封升级和被动）C 中位 4.5。41 题这种“护驾被封就贴脸杀”的局面要在破釜之后多看 2 层：破釜（深度剩 2）→ 汉安静一步 `车4,4→3,4`（剩 1）→ 楚应（剩 0）→ 汉 `车→3,9` 不吃子的将军——多 1 层时这一步落在只算吃子的静态搜索（`:141`）里，看不见。**评审两边实测**：多 1 层 41 题 0/3（根上分数和 dev 一模一样）、36/37 0/1，着法 0/42 变，节点 P90 +20%——花了节点没改棋；多 2 层 41 ✓ 3/3、36 ✓、37 ✓、24 不退，但汉方局面节点中位 ×1.29、**P90 ×2.42、最大 ×2.71**（种子 21 最坏局面 ×2.3～2.6，单局面 96528 节点，超 6 万预算）——过不了第 6 道闸。只对第一个组合延伸 P90 也有 ×1.91。所以草稿的 G1(b)“多算一层”**撤回**，换成 §4.2 (b′)。

### 4.2 方案（`BFAI_G1A` / `BFAI_G1B` / `BFAI_G1C`，默认都 1；G1B 的默认以 Code 实测 P90 为准，见 §4.5）

**(a) 对称化：汉方第 1 层里楚的破釜要“值得楚用”才算数**（`:236–242`）
```
const need = best + (hot(k) ? 0 : pofuMargin());                      // best = 到这里为止楚最好的普通应着
for (const k of pf) {
  const lo = Math.max(alpha, need - 0.01), hi = Math.max(beta, lo + 0.01);   // 窗口不能倒置
  const v = w ? … : -ab(k.S, dep, -hi, -lo, ply + 1, ext);
  if (v < need) continue;                                              // 楚不会为这点便宜用掉一局一次的破釜
  if (v > best) best = v;
  if (best > alpha) alpha = best; if (alpha >= beta) break;
}
```
- **窗口 bug（两位评审都抓到）**：草稿写的是 `(-beta, -max(alpha, need − 0.01))`，当 `need − 0.01 ≥ beta`（best 离 beta 不到 3.01）时 alpha > beta，子节点算完第一步就截断、返回的只是随便一步的分数。评审实测种子 7002 的 11 个汉方局面里 630 次破釜子搜索 **370 次（59%）倒置**；按原样写 41 题（多 2 层）不过，修成 `hi = max(beta, lo + 0.01)` 后过。修好后全关时和 dev 完全相同。
- `pofuMargin()`：默认 **3**（楚自己的门槛是 5，留 2 分余量防人类楚方更冲动）；`CFG.beishui && CFG.beishui.on` 时 **1**（背水下楚方当防守手段用，预筛门槛 2）。两处（这里和 G4 的预筛）读同一个函数。原型里拿 {0, 3, 5} 对打定。
- `hot(k)`：**位置上致命的组合不设门槛**——评审指出“破釜吃掉汉士 / 相、把楚车马带进九宫，静态只赚两分多、第 3 步以后成杀”这类楚方根上核对比汉方第 1 层看得深、会用，汉方有门槛就漏了。判定：`pressure(k.S, 'b') > pressure(S, 'b')`（`:260`，楚进攻子在汉帅 4 格内多了）或 `k.ev` 里有 `e.e === 'kill' && e.s === 'r' && (e.t === 'a' || e.t === 'e')`（吃了汉守子）。O(子数)。
- 已知误差：`best` 里含“先升级再应”的分支值，升级分支的内层调用里 alpha 已抬高，普通着法可能 fail-low，best 只是上界、need 偏大，少数破釜线会被错丢。有界，不处理。
- **已核实**：节点合计 −1%～−7%、最大 +8%；着法 1/42 变；24 ✓。

**(b′) 汉方根上陷阱核对**（新设计，替代草稿的 (b)；写法照搬楚方根上核对破釜 `:433–447`）
- 搜索中记一笔：`ab()` 第 1 层的破釜循环把 `best` 抬高时，把“抬高前的普通应着最好值”记到一个模块变量；根循环（`:396`）每算完一个根着法 k 就取走，存成 `k.plain`（从汉方看 = −那个值）。普通应着已经把这步驳倒（第 1 层先截断、没进破釜循环）的根着法不记——那是本来就坏的着法，不是被破釜压下去的。
- 主搜索结束后（`:421` `bestV` 之后），`if (G1B && me === 'r' && pfPly === 1 && bestV < WIN / 2)`：候选 = `kids.filter(k => k.plain != null && k.plain > bestV + G1B_MIN)` 按 `plain` 降序取 **前 2 个**（`G1B_MIN` 默认 **2**）。对每个候选：设 `pfExt = 2`（第 1 层破釜循环里 `dep = max(0, depth − 1) + (前 2 个组合 ? pfExt : 0)`，**不占** `CX` 将军延伸预算——破釜后的反击本来就是将军链，占了就少一次），`k.v2 = −ab(k.S, d1, −INF, −need + 0.01, 1)`，`d1 = max(1, depthDone) − 1`，`need = bestV + 0.01`；`v2 ≥ need` 且最高的那个接管 `pick`。预算：节点模式 `nodeCap = nodes + 0.3·L.nodes`，时间模式 `deadline = now + max(300, 0.3·budget)`；超时就保留原来的着法。算完 `pfExt = 0`。
- 为什么能过 41【推断】：`车2,3→8,3` 不算破釜是最好的一步（评审：完全不提防破釜的电脑能答对 41），算破釜时被压到前四之外 → 被记成候选；重算时破釜线多 2 层 → 看到 `车→3,4`、`车→3,9` 贴脸将死（评审全树多 2 层 3/3 ✓，这里是同一个搜索只对这一步做）。24 题：`炮吃卒` 同样被记成候选，重算后破釜吃车的账还是亏 → `v2 < need`，保留原着法 `车6,4→6,0`。
- 为什么便宜【推断】：全树多 2 层的开销（+74%）摊在第 1 层的 ≈35 个根着法上；只重算 1～2 个，再加它自己的子树（空窗口，便宜）→ 每次触发 +5～15%，30% 封顶。
- 触发多频繁【已核实·代理量】：拿评审 1 现成的 25 个汉方局面（都未用破釜）比较“dev”和“汉完全不提防”的根分数（提防只会压低根分，所以差值就是“被破釜压下去的最好着法能好多少”）：差 >0.5 的 13/25，**差 >2 的 5/25**。按 `G1B_MIN = 2`，大约 **1/5 的汉方步**触发。P90 要实测（§4.6），**超过 1.3× dev 就把 G1B 默认改 0**。
- 36、37：评审全树多 2 层各 ✓；(b′) 能不能把它们的答案步记成候选要实测，不当门槛。

**(c) 封锁期估值项：按引擎实际封了什么算**（`:86–87` 改写）
- 每次 `think()` 开始探一次 `lock = { up, passive, turns }`：

### 4.5 风险和代价

- (a)：**已核实** 节点 −7%～+8%。真风险是对人类楚方：人会为净赚 1～3 分的破釜（炮先吃炮架兵再吃马之类）出手，电脑楚方从来不会；汉方会更常把马、炮留在这种位置。默认 3 的余量和 `hot()` 豁免就是为此；网页上“楚方是人”时把 margin 降到 1（`think` 不知道对手是谁，要 chat 在界面传一个标志，可选）。
- (b′)：**推断** 触发 ≈1/5 汉方步、每次 +5～15%、30% 封顶 → 汉方步平均 +1～5%，P90 +15～30%。时间模式每步最多拖 0.3·budget（和楚方的核对一样）。**默认值以实测定**：42 个局面上 P90 >1.3× dev 或没算满 3 层的局面多 >2 个 → 默认 0。
- (c)：探一次 ≈0.1 ms；`score()` 里的被动求和放进 `:44–48` 已有的循环、查预先按 (t, s, lv) 缓存的表，每节点 +1～2%【推断】，而且只在 `pf > 0 && lock` 时。
- 会变弱的局面：(a) 后汉方对“楚破釜只赚 3～4 分但位置上致命”的线失察——`hot()` 盖住进九宫 / 吃守子两类，其余的正是楚方电脑也不会用的；对人类楚方有一点。

### 4.6 怎么验证

1. 考卷：24、31～35 不退；41 ≥2/3（(b′) 开）；36、37 校尉和 `--level hard --nodes hard=200000` 各记一次。
2. 代价（评审的 42 个局面 + `c_worst2.js` 三个最坏局面 + `bfpage_timing.js --side r`）：(a)(b′)(c) 各自和合起来的第 3 层节点 P90 / 最大、没算满 3 层的局面数；P90 和最长 ≤ 1.5× dev。

**白话**：现在的汉方电脑一看到“对方可以破釜吃我的子”就先躲，哪怕对方电脑根本不会为这点便宜用掉一局一次的破釜（人可能会——所以留了余量，而且吃士相、冲进九宫的破釜照旧提防）。改完以后它会按对方的账来算：赚得不够多的破釜当它不存在；真会来的照躲。另外它会多做一件事：主搜索挑完着法后，看看有没有哪一步“要不是怕破釜本来最好”，把那一步单独再算一遍，这回破釜之后多看两步——比如第 41 题，车串打双马、故意让对方破釜吃车，对方一破釜护驾被封，我的两血车贴脸绝杀。要说实话的是：**按现在的规则，封锁期本身几乎不值钱**，“放它破釜再反击”多数时候是亏的，电脑算完也会这么判；要让设计者说的“算账、下饵”经常成为好棋，得靠方案 A 这类让封锁也封住升级的规则——那时电脑会自动把这笔账算进去。

## 5. 我们的分析里哪里错了或漏了

1. **“士象几乎不升”是错的，“升得被动”才对**（H24：汉 a2 75%、e2 50% 的局里升过，全是被捉 / 被将军才升）。少的是技能级，而现行价目下本来就不划算。真缺口只有“升完立刻能用”，**而且只有被动本事**（主动技能解锁要冷却一回合）。齐射 / 践踏 / 飞越 0% 更多是规则（象不能过河、践踏要在家门口吃到子）。
2. **“前三名把守子挤掉”是错的**，是第 308 行（430 对 5）。
3. **“电脑不知道进账和上限”只对一半**：进账在树里引擎自动发；缺的是己方第 2 层的升级分支。上限现行节奏下碰不到。
4. **G1 在现行规则下的封锁期回报 ≈0**，该修的是不对称；C 是给方案 A 准备的。草稿用来证明“防过头”的 56% 读反了（见 §4.1）；真实量是“关掉提防 32% 的汉方着法会变，其中 3/8 躲对了”。
5. **“G4 从 G1 里自动长出来”不成立**：汉下饵要破釜之后多 2 层（全树太贵，所以做成根上核对），楚拒饵是楚根上核对多 2 层——两者独立，G4 更便宜、更确定，先做。
6. **36、37 题**：“任何通用改法都过不了”说过头了——全树多 2 层就过（评审实测），只是贵得过不了闸；(b′) 能不能过要实测。它们仍不当门槛，必须和 24 一起看。
7. **草稿的四处硬伤**（评审抓的）：G1(a) 窗口倒置（59% 的破釜子搜索）；G1(c) 探针因 `turn` 永远答“封”；G2 的“将军奖励”门永远成立；G3 公式混进升级本身的分（15 次触发 14 次假）。都改了，见各节。
8. **草稿 §5.6 说过头了**：“封锁期里汉方的军功更值钱，电脑看得见就会攒”——G1(c) 和 G2 里没有任何一项提高汉方军功的价值，不会出现“提前攒军功等封锁期”。删。
9. **背水**：`bfai_beishui.js` 改的是根上静态预筛（4.5→2、被将军不设门槛），不是 `PF_MIN`；“车马炮比对方少”是 `CFG.beishui.fewer[s]`，不是 `beishui.on`；电脑没有 `artOpen` 接口，要读 `fewer` 就得抄一遍引擎规则——现在默认不读（§4.2 c）。
10. **Code 的“1.3～1.9 子力”是 9ff 电脑量的**，dev 没重量；用 dev 的 `pfPly = -1` 对照复测。
11. **耗时要看尾部**：dev 第 3 层 P90 ≈4.5 万、单局面 9.3 万节点；6 万上限下任何 +20～50% 的尾部都让第 3 层算不完、悄悄变浅。每个开关报第 3 层节点 P90 / 最大和没算满的局面数，不报平均。G1(a) 省、G2 / G1(b′) / G4 费，四个一起开要专门量。
12. **验收别靠 300 局统计行**：预测的“a4 升一两个点”“首次升到 3 级提前”都在噪声里；按触发记数。SPRT 只给改变率 ≥ 几个百分点的组合。
