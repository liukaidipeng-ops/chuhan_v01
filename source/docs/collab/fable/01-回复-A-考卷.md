## 问题 2：有没有电脑没见过的保留题

### 2.1 结论：没有。【已核实】

- 题目全在仓库：`tools/bfai_exam.js`、`tools/bfai_exam_games.json`，在 Code 的分支上，chat 定期 fetch（H5“每次轮询顺手 git fetch”）、合并（H12“破釜反击 5 题收到，已合进 dev”）、自己跑（H15“考卷校尉 111/111”；H19“考卷含你新出的‘战略’题”）。
- 出题过程中的候选（`scratchpad/exam_candidates.json`、`wf_gap/`）只是暂时没推，最后都会并入；而且 scratchpad 容器回收就没了（NOTES 2.3），**藏不住秘密**。
- 复核和实1 裁判都用被考电脑自己的搜索。

### 2.2 方案：承诺种子 + 现生成 + 事后公开（不需要保密）

既然藏不住，就让题目**在电脑定稿之后才产生**，并且每个候选版本一批新题：

**原理**：种子 = 候选 `src/bfai.js` 的 git blob 哈希前 8 位（`git hash-object src/bfai.js`）。电脑文件一改，哈希就变，题就变；谁也不可能提前知道题。跑完把题和结果一起提交公开（这批题就“烧掉”了，下一版自然换新）。

**文件和命令（给 Code 实现）**

```
tools/bfai_holdout.js
  --ai src/bfai.js            被测（可以给多个：--ai A,B,C，同一批题对比）
  --prev git:25eb911          上一版，同一批题一起考，报差值
  --gen git:25eb911           出题用的电脑（固定 = 线上版）
  --judge git:b18c278[,git:25eb911]   裁判（固定、写在 bfai_gate.json 的 holdout.judge；永远不能是被测版本本身）
  --seed auto                 默认 = 被测文件 blob 哈希前 8 位；--seed N 用于复现 / 审计
  --games 8 --open 6 --gen-nodes 12000 --from 9 --step 5 --to 70
                              8 局自对弈，前 6 步高随机，之后校尉档省节点；第 9 步起每 5 步抽一个局面（奇数步长 → 汉楚各半）
  --games-file docs/games/*.txt   可选：把用户导出的对局里电脑走的每一手也抽进来（标签“实战”）
  --judge-nodes 200000 --test-nodes 60000 --runs 1
  --out docs/holdout/<被测短哈希>-<seed>.json
```

**每个局面怎么算分**（原型 2 已验证可行，`holdout_proto2.js`）：
1. 裁判（霸王档、noise 0、按节点收手）给出最好一步 B；
2. 走 B，再让裁判在新局面上搜一次，取反 = vB；
3. 被测走出 P（校尉档 6 万节点）；P ≠ B 就走 P 再让裁判搜一次 = vP；
4. 损失 = max(0, vB − vP)，封顶 20；≥2 记失误、≥4 记漏着。
5. 报：平均损失、和裁判一致率、失误 / 漏着数；按标签分组：汉走 / 楚走、封锁期（`cnt.b < fx.pf`）、楚可破釜、汉可召回、第 14～17 回合、被将军、有子被捉、决战、实战。标签子集就是四个战略缺口的统计量。

**为什么不筛“有明确最佳着法”的局面**（原型 1 的教训，`holdout_proto.txt`）：按“第一第二名分差 ≥1”筛，31 个局面只剩 5 个，全是“白吃车 / 炮 / 士”，三个版本 10/10 全对。版本差距藏在大量“差零点几分”的局面里，只能靠损失累加来看，不能靠筛题。

**原型 2 结果【已核实，仅作示范】**（4 局 25eb911 自对弈，36 个局面，汉楚各 18；裁判 b18c278 霸王档 15 万节点；被测校尉档 6 万节点；机器满载下 808 秒）：

| 版本 | 和裁判一致 | 平均损失 | 失误(≥2) | 漏着(≥4) | 汉走 / 楚走平均损失 |
|---|---|---|---|---|---|
| b18c278 | 29/36 | **0.26** | 2 | 0 | 0.24 / 0.28 |
| 25eb911 | 23/36 | 0.47 | 3 | 1 | 0.60 / 0.33 |
| 9ff64a4 | 23/36 | 0.48 | 3 | 1 | 0.62 / 0.33 |

两点必须说明：裁判就是 b18c278 自己，它和自己的校尉档更容易一致，所以 0.26 偏好看——正式工具里裁判必须是固定版本，且被测 = 裁判时自动换上一版；36 题太少，只能说明“这个量法能分出差别”，不能说明差多少。有意思的是执汉损失差距大（0.24 对 0.60），和“新版执汉赢得多”一致，但同样是推断。

**轮换**：每个候选自动一批新题（种子跟着哈希走）。要同批比较多个版本（像今天四版）就显式给 `--seed`。老批次留在 `docs/holdout/` 当公开回归题，可以不定期挑“所有版本都错”的局面转成正式考题。

**计分 / 门槛**：先只量基准（null）；攒 3 个版本后定：候选平均损失 ≤ 上一版（同批题），漏着数不多于上一版。它是诊断，不替代对打——对打仍然决定能不能上线。

**chat 以后看到结果，怎么保持诚实**：
1. 题和结果跑完才公开，下一版题目不同，看旧题只能修真毛病；
2. 种子来自文件哈希，想“对着题调”就得改文件，一改题就换；
3. 裁判、出题电脑、节点数都固定并写进 JSON，任何人能用 `--seed` 复现核对；
4. 被测永远不当自己的裁判；
5. Code 跑、Code 记 NOTES；chat 可以复跑验证，但不能改裁判版本（改 `bfai_gate.json` 的 holdout 项需要 Code 提交）；
6. 剩下的唯一“漏洞”是针对出题电脑和裁判的通用改进——那正是我们想要的。

**成本**：满载机器上 36 局面 × 3 版约 13 分钟；空闲时约 4～5 分钟。正式 80～100 局面 × 2 版，估计 10～15 分钟（推断）。放进总闸的完整模式，`--quick` 可缩到 40 个局面。

## 三类结论汇总

**必须改**
1. 考卷不再用总分给版本排序；门槛改为“100% / 逐题不退步”（证据：9ff 108 > 25eb911 101，对打相反；3 千节点 35/37）。

3. 考卷加“裁判损失”连续分（不要用 `think.last.top` 的分差，窗口外只有上界）。

**建议改**
4. 战略题每缺口 ≥3 道，对照题入卷、成对计分；缺口③④ 以统计为主。
5. 补：楚方视角（何时破釜 / 鸿门宴）、四面楚歌、安静好棋、防守、残局；把“别走某步”的 5 题标为回归题、不计强弱。
