## 0. 一页总结

|---|---|---|---|---|

**哪里错了或漏了（详见 §5）**：① “士象几乎不升”不对——H24 里汉方 a2 在 75% 的局里升、e2 50%，升得不少，只是**都是被动的**（被捉 / 被将军才升）；少的是升到技能级（a4 10.7%、e3 11%、e4 0.7%），而现行价目下升到技能级本来就不划算（象三升四静态 −0.53），所以 G3 只该修“升了立刻有用”这一种，**不该**让电脑平时多升士象。② “前三名挤掉守子”不对，是第 308 行。③ “电脑不知道第 16 回合进账”只对一半。④ 现行规则下 G1 的“封锁期回报”本身就接近 0，别指望 G1 在现行规则下翻盘；它的价值在方案 A（或任何会封升级的规则）下才大。⑤ 第 36、37 题要 6 层并且第 4 层含己方升级，校尉档靠任何通用改法都过不了，别拿它们当 G1 的验收。

## 1. G3 · 士 / 象（规则无关，先做）

### 1.1 问题是什么

**【已核实】升级候选怎么被砍的**（dev `bfai.js:287–314`，`upgradeCands()`）：
- `:305`：`must` = 大子 / 守子正被捉（`threatened`）、或正被将军；
- `:308`：`if (defender && !must && !(p.t === 'a' && heavy && p.lv < 2)) continue;` ——**没被捉的士象一律不进候选**，唯一例外是“对方有两血进攻子逼近时士一升二”；
- `:309`：攒车钱 / 攒终极时非车不升；
- `:313`：`cand.slice(0, 3)`。

我在 dev 电脑上跑了 3 局自对弈（3000 节点，146 步），把每一步的全部升级候选按“被哪条砍掉”分类：
| 守子（士象）候选 | 数量 |
|---|---|
| 被 `:308`（没被捉就不升）砍掉 | **430** |
| 被 `:313`（只留三名）砍掉 | 5 |
| 留下 | 37（其中 31 个是 `must`） |
非守子被 `:313` 砍掉 82 个。**所以 Code 在 NOTES 1.5 里写的“只留前三名把守子挤掉了（象升级静态 −0.53 排最后）”诊断错了**：象根本没进那张表。

**【已核实】考题 39、40 在 dev 上的候选表**（我把两题的局面原样摆出来跑 `upgradeCands` 的各阶段）：
- 39 升象践踏：象 lv3→4 花 5 功，静态 `gain = −0.53`，`must=false` → `:308` 砍掉。但**升完之后这枚象立刻能走的最好一步** `(4,7)→(6,5)` 吃兵触发践踏，连杀 5 子，局面分 **+15.2**（升之前同一步是 −7.76）。留下的候选只有车（+3.24）和兵——电脑选了升车出车（−3.52）。
- 40 升士禁卫斩车：士 lv3→4 花 4 功，`gain = −0.30`，没被捉（楚车攻击 1 打不死 3 血士）→ `:308` 砍掉。升完立刻 `(4,1)→(4,2)` 斩车 **+7.32**；升之前这枚士一步也吃不到东西。电脑选了升车吃车（−1.28，打一下被弹回）。
- dev 在战略类 **0/18**（我跑的，校尉 6 万节点 3 次），和 b18c278 一样；线上 25eb911 是 9/18——它的 `pickUpgrade`（25eb911 `:196–224`）不筛守子，六个候选都用两层搜索比一遍，所以碰得到。

**【已核实】这是不是个真缺口（看 300 局统计，H24）**：汉 a2 75.3% 的局升过、a3 42.3%、e2 50.0%；楚 a2 58.7%、e2 40%。**士象升得并不少**，只是全是 `must`（我那 37 个留下的守子候选里 31 个是 `must`）。少的是 a4（10.7%）、e3（11%）、e4（0.7%）——技能级。齐射 / 践踏 / 飞越 0% 的根子一半是规则：象过不了河、践踏要在家门口吃到子才触发；现行价目下象升到四级要 2+3+5=10 功，估值只给 +0.4/+0.9（`:32`），所以静态永远是负的——**平时不升是对的**，Code 的军功实验（极限升级 −16、攒军功 −34）也支持“别乱改升级意愿”。
真正值钱的只有一种情形：**升一级立刻解锁技能、而且这一手就能用上**（39、40 都是这种）。我在 146 步自对弈里数了：到达技能级的升级候选 66 个，其中升完立刻多出“能吃到子的新着法”的 **0 个**——所以这种机会在实战里稀少，但一出现就是一整局的胜负（39 题一步五子）。结论：**G3 是真缺口，但很窄；修窄的那一条，别碰宽的。**

### 1.2 方案（`BFAI_G3`，默认 1）

挂在 `upgradeCands()`（`:300–311` 的循环里），在 `:308` 之前加一条“立刻有用”判定：

```
// G3：升一级就解锁技能（含被动）、而且升完这一手就能多吃 / 多打到子的升法，当 must 看待
const unlock = G3 && lvInfo(p.t, p.s, p.lv + 1).skills.length > lvInfo(p.t, p.s, p.lv).skills.length;
const useNow = unlock && immediateGain(S, T, p) >= G3_MIN;   // 默认 1.5
if (defender && !must && !useNow && !(…原来的士一升二例外…)) continue;
if ((saving || hoard) && p.t !== 'r' && !must && !useNow) continue;
cand.push({ …, must: must || useNow });
```

- `lvInfo` 用 `BF.levelInfo(t, s, lv)`（`bingfa.js:854`，已导出，按 `CFG.skills[k].level`、`CFG.skillLevel`、`maxLevel` 算）。我核实了现行规则的解锁表：兵 2→3 拒马、3→4 神速/回防；士 2→3 护驾、3→4 铁甲禁卫；相 2→3 飞越、3→4 齐射；象 2→3 飞越、3→4 践踏；马炮 2→3 踏营/霹雳；车 2→3 冲阵。规则改了（比如“四级技能降到三级”那组）表自动变。
- `immediateGain(S, T, p)`：对**这枚子**在升级前的局面 `S` 和升级后的局面 `T` 各枚举一遍它自己的吃子 / 技能着法（`A.gen(·, true)` 过滤 `it.p.id === p.id`），每个 `BF.attempt` 一次、用 `score()` 打分，取最大值之差。这正是我在 39/40 上量到的 +15.2 对 −7.76、+7.32 对“无”。它天然覆盖禁卫（新走法）、践踏 / 霹雳 / 冲阵（同一步结果不同）、飞越（塞象眼解开）、齐射 / 踏营（新的打击目标）。
- `:313` 的 `slice(0, 3)`：**不改**。`must`（含 `useNow`）本来排前面，三名够用；放宽会让根节点变宽、校尉变浅（S13：升级并进根节点已经让节点 ×1.7）。
- `:425–427`（给士象的升法要比“不升”好 0.4 才选）：**不改**。39/40 的差距是十几分，0.4 拦不住；平时它正好防止乱升。
- 校尉以下（`L.depth < 2`，`:327–331`）不动。

### 1.3 怎么从 CFG 读规则

全部走 `BF.levelInfo` / `BF.ai.gen` / `BF.attempt`：哪一级解锁什么、技能有没有目标、践踏踩到谁，都是引擎说了算。改价目（`CFG.upgrade.cost`）只影响 `upCost`→`upgradeState` 能不能升；四级技能降到三级、被动改主动、新增技能（回春）都自动跟。背水 / 方案 A 与它无关。

### 1.4 预计效果

- 考题：39、40 校尉 6 万节点应 **3/3**（候选进了根节点搜索，深搜复核已给 +18.7 / +14.9）；第 18 题（没用的时候别升士象）必须保持 3/3——`useNow` 要求“立刻多吃到子”，18 题没有。
- bfsim：`升级` 表里 a4 / e4 的行略升（从 10.7% / 0.7% 往上一两个点【推断】）；`行动` 表里铁甲禁卫、践踏、齐射从 0～5% 略升；`军功来源·击杀` 不变或略升。**不该动**：a2/e2（它们本来就是 must 升的）、r2/r3（不改攒车逻辑）。
- 对打：**±10 Elo 内**【推断】。机会稀少（146 步里 0 次），但每次是整局的量；代价是极少数回合多 1 个根候选。

### 1.5 风险和代价

- 变弱的局面类型：`immediateGain` 只看一步静态分，可能被“升完吃一个子、下一步被反吃”的假机会骗进候选——但候选进的是**根节点搜索**，三层会把它比下去，只花节点不改着法。真正会错的是校尉以下（新兵不走这条）。
- 每步代价：到达技能级的候选 ≤ 66/146 步 ≈ 每步 0.45 个；每个候选枚举该子的吃子着法（士象 ≤ 4、车 ≤ 17），每次 `attempt` ≈ 0.02 ms（c_pofu_cost：250 次 5 ms）→ **每步 < 1 ms，不计节点**。最坏局面（种子 21 第 16 步）不涉及。时间模式：这段在根上、在 `nodes` 计数之外，和 `:234` 一样补一句 `if (now() > deadline) throw TIMEOUT`——实际远到不了。
- 根节点多 1 个候选时节点 +4%【推断：b18c278 三个候选 +70%，UPK 后 +11%】。

### 1.6 怎么验证

1. `bfai_exam.js --only 战略`：39、40 要 3/3；`--only 军功`、`--only 技能`（含 18）不退。
2. 对打：`--match G3版,git:b18c278 --sprt -30,10`，换边。**有效** = 通过（不明显变弱）且 bfsim 300 局里 a4/e4/禁卫/践踏行往上、r2/r3 不动；**失败收回** = 不通过，或 18 题退步，或 r2 首次升到的回合推迟 >1。
3. 关掉 `BFAI_G3=0` 时着法逐一同 dev（Code 的 `same_moves.js`）。

**白话（给设计者）**：电脑原来有个死规矩“士和象没被人捉住就不花钱升级”。改完以后，只有一种情况它会破例：升这一级马上就能用上新本事、而且这一手就有收成——比如四级士能直走一格，正好一刀砍死钻进九宫的两血车；或者四级象踩着过河兵，把挤在河边的车马炮一圈踩死。平时它还是不会给士象乱花钱。

## 2. G2 · 军功规划（规则无关，第二做）

### 2.1 问题是什么

**【已核实】电脑“不知道”进账这句话只对一半**：
- 进账是引擎在 `attempt → endTurn` 里发的（`bingfa.js:457–459`：楚方走完、`round(S) >= autoIncomeFromRound` 时两边各 +1，`round = floor((cnt.r+cnt.b)/2)+1`，`:110`）。搜索树里每过一个楚方回合，军功就已经加上了——电脑的搜索**看得见钱到账**。
- 看不见的是**己方下一回合的升级**：`:332 upPly = 1` 只在第 1 层给**对方**开“先升级再走”（`:186–204`），己方升级只在根上（`:326`）。所以“这回合别花、下回合进账正好升三级车绝杀”（第 38 题）这条线在树里不存在：dev 在 38 题选 `车4,4→8,4×炮 10.6`，标准答案 `车4,4→4,7` 连前四名都没进（我跑的 verbose）。
- 军功估值 `:77 v += 0.3 × (军功差)`，线性、无上限意识；但**上限几乎碰不到**：我扫了 scratchpad 里 6 份 300～400 局的 JSON（每 5 回合采样），军功 ≥28 的采样点占 0.4%～2.0%，终局军功 ≥28 的方局 2～23/800；H24 里 R30 平均军功汉 4.3 楚 4.2。3 局自对弈里精确量的“贴上限浪费” = **0**。所以“贴上限浪费”这一项在现行节奏下是空的——写上它只是为了规则改了（比如军功涨价、回合更长）以后不出事。
- 已有的 `saving`（`:294–296`：车差 3 功以内就攒）在 38 题已经生效（7 对 8），电脑没乱花钱；它错在把车调走。**所以 G2 的核心是搜索，不是估值。**
- 我量了“差一笔进账就升得起”的频率：3 局里第 15 回合起的 62 个回合中 **36 个**（58%）存在“某枚子的升级价 ∈ (军功, 军功+1]”。这个触发不稀少，所以分支必须收得很窄。

### 2.2 方案（`BFAI_G2`，默认 1）

**(a) 搜索：第 2 层给己方开一个“刚够钱”的升级分支**（挂在 `ab()`，`:186` 的 `upPly` 块旁边）：
- 根上（`think()`，`:326` 之后）算一份 `soon`：己方每枚子 `c = A.upCost(p)`，取 `c > merit_root && c <= merit_root + G2_LOOK` 的子，`G2_LOOK = CFG.merit.autoIncomePerRound`（现行 1）；只在 `round(S0) >= CFG.merit.autoIncomeFromRound - 1` 或该子的“刚够钱”能由将军奖励（`CFG.merit.checkReward`）凑出时才算；按 `score(T) - base` 排序只留 **1 个**（车炮马优先，守子走 G3 的规则）。
- `ab()` 里：`if (G2 && ply === 2 && side === rootSide && !S.upgraded && soon)`：找到那枚子（按 id 扫板），`A.upgradeState(S, at)` 非空（说明这条线里钱真的到了）就把升级后的局面当一个分支，**只接着算升的那枚子自己的着法**（和 UPK 的 `own` 同一思路，`:339–340`）——38 题正是“升车→车吃马将军”。深度同层（和 `:199` 一样 `depth - extd`）。
- 第 2 层之外不开；楚方根上破釜核对（`:438–444`）的子树里也适用（它的第 2 层就是楚方自己）。

**(b) 估值：贴上限的军功不值钱**（`:77`）：
`usable(m) = min(m, cap − headroom)`，`headroom = 2 × autoIncomePerRound`（round ≥ fromRound 时，否则 0）；`v += 0.3 × (usable(me) − usable(opp))`。等于告诉电脑“再过两回合进账会白扔，先花”。现行节奏下几乎不触发（见 2.1），代价 O(1)。

**不做的**：改 `saving`（Code 的实验：不急着升车 −46、攒军功 −34），改 0.3 的斜率，极限升级（−16，而且用户说“要它划算得改规则”）。

### 2.3 怎么从 CFG 读规则

- 读 `CFG.merit.autoIncomeFromRound / autoIncomePerRound / cap / checkReward`（`bingfa.js:15–19`）。规则改成“第 16 回合起主公技”不影响它；“arts-from16”预设只动 `generalArts.fromRound`。
- 进账时点不自己算：由 `attempt` 在树里发（`:457`），所以 `G2_LOOK` 只是“往前看多远”的窗口；即使以后进账改成每回合 2 功、或从第 1 回合起，第 2 层那个分支一样对（`upgradeState` 用的是树里的真实军功）。
- 车升级涨价（15/15/20）：`upCost` 变，`soon` 自动变；分支数不变。

### 2.4 预计效果

- 考题：38 校尉 **3/3**（根深 3：第 1 层楚应、第 2 层升车+吃马将军、第 3 层楚应将、被将军时 `:180` 再往下一步 → 第 4 层杀，够）。38 的对照（第 10 回合）要照样吃炮。

## 3. G1 · 封锁期的账（依赖规则，第三做；写法通用）

### 3.1 问题是什么

**【已核实】现在的电脑怎么看破釜**（汉方走时）：
- `:333`：只要楚的破釜没用，`pfPly = 1`——第 1 层（楚的应着）里加破釜组合。
- `:162–171` `pfList` / `:230–231`：组合先按静态 `q = score(破釜后) − score(破釜前) >= 3` 筛，留最狠 4 个；`:238` 破釜之后那条线深度 `depth − 1`（和普通应着一样）。
- 破釜之后 `used.art.b = 1`，估值 `:80` 的兵法价 3 分自动掉——所以搜索里已经隐含“楚用掉破釜要付 3 分”。
- 封锁期估值 `:86–87`：只有开了 `PFC/PFA` 才有，默认 0；`:323` PFD 多算一层也默认 0。
- 楚方自己（`:433–447`）：破釜候选要比最好的普通走法**搜索值高出 `PF_MIN = 5`** 才用（`:434`），而这 5 分是在估值已扣 3 分兵法价之上。

**所以不对称**：汉方把“楚破釜后搜索值只要比普通应着高一点”的组合都当真；楚方自己只在高出 5 分（加上估值里的 3 分，等于静态要赚 8 分上下）时才用。我在 dev 上量了 3 局（3000 节点）：汉方走子后、楚破釜未用的 73 个局面里，**41 个（56%）有 q ≥ 3 的破釜组合**（就是汉方刚才在第 1 层算过、怕过的）；其中 q ≥ 8 的 10 个；楚方实际用破釜 **0 次**。H24 的 300 局里楚方 44% 的局用破釜、每局最多一次——按汉方每局约 30 步算，“怕”的频率是“真发生”的十几倍【推断，比例用的是两组不同样本】。Code 量的“一直防比完全不防强 7 个百分点，但先丢 1.3～1.9 子力”（NOTES 1.1，9ff 电脑）说明防是对的、防的量过了；**现行规则下过度的那部分主要就是这个不对称**，不是封锁期没算——Code 自己量的 C 在现行规则下 46 个局面 40 个为 0（NOTES 1.2）。

**封锁期的账在哪里才值钱**：方案 A（封升级和被动，C 中位 4.5）、以及 36/37/41 这种“护驾被封就闷杀”的局面。41 题：标准答案 `车2,3→8,3` 不在 dev 前四名；它要求楚破釜吃车之后，汉 `车4,4→3,4`（安静一步）再 `→3,9` 贴脸——从根算：第 1 层破釜（深度剩 2）、第 2 层汉安静步（剩 1）、第 3 层楚应（剩 0 进静态搜索，看不到非吃子的将军）。**多算一层就看见了**。36/37 要第 4 层含己方升级（升马两血再跳）再两步杀，共 6 层——校尉档任何通用改法都到不了，只有霸王档可能。

### 3.2 方案（`BFAI_G1`，默认 1；三部分可在原型里各自再带一个子开关便于 Code 拆着测）

**(a) 对称化：汉方搜索里楚的破釜要“值得楚用”才算数**（`:236–242`）
```
const need = best + G1_MARGIN;                    // best = 到这里为止楚最好的普通应着
for (const k of pf) {
  const v = … -ab(k.S, dep, -beta, -Math.max(alpha, need - 0.01), ply + 1, ext2);
  if (v >= need && v > best) best = v;            // 楚会用，它得到 v
  if (best > alpha) alpha = best; if (alpha >= beta) break;
}
```
`G1_MARGIN` 默认 **3**：楚自己的门槛是 5（`:434`），汉方留 2 分余量防人类楚方更冲动；原型里拿 {0, 3, 5} 对打定。窗口变窄，这部分**省节点**。

**(b) 兵法延伸：破釜之后那条线多算一层**（`:238`）
`dep = Math.max(0, depth - 1) + (ext < CX ? 1 : 0)`，并把 `ext + 1` 传下去——和将军延伸（`:177–178`）共用同一个 `CX=2` 的预算，所以任何一条线最多延伸 2 次，不会失控。只对 `pf` 里前 2 个组合延伸（第 3、4 个用原深度），控制最坏局面。

**(c) 封锁期估值项：按引擎实际封了什么算**（`:86–87` 改写，`:80` 兵法价改条件）
每次 `think()` 开始，若楚的兵法还在手里，取一个破釜组合的结果局面 `T`（`pofuPairs` 第一个即可），在 `T` 上探一次引擎：
- `blocksUpgrade`：把 `T` 的楚方军功临时设成 99，对任一楚子调 `A.upgradeState` → 为 null 则封升级（bfsim 的方案 A 预设正是包了 `BF.ai.upgradeState`：`bfsim.js:140–141`，所以探得到；以后 chat 写进引擎加了 `CFG.generalArts.pofu.lockUpgrades` 之类的键，优先读键）；
- `blocksPassive`：`T` 里若有带被动走法技能的楚子（`levelInfo(...).skills` 含 `CFG.skills[k].passive` 的），比较 `A.moveTargets` 在 `T` 和在“把 `T.fx.pf` 清零的副本”上的差；没有这种子就跟 `blocksUpgrade`；
- `lockTurns = CFG.generalArts.pofu.skillLockRounds`（`bingfa.js:39`）；`fx.pf` 的读法电脑已经在用（`:86`）。
然后 `score()` 里（只在 `pf > 0` 时，和现在一样）：
`C = Σ(被封的主动技能 w_k) + [blocksPassive] Σ(被封的被动 w_k) + [blocksUpgrade] × (2.5 + 0.3·min(楚军功,10))`，乘 `min(1, pf / lockTurns)` 线性退掉。
`w` 是电脑常数（像 `VAL`）：护驾 `0.4 + 0.5·min(3, attR)`（汉有子压在楚将跟前时护驾被封最要紧——36/37/41 的机制）、冲阵 0.3、霹雳 0.3、踏营 0.2、拒马 / 飞越 / 齐射 0.1；被动：践踏 0.3、禁卫 0.3、神速 / 回防 0.1。哪些技能被封、哪枚子有哪种技能，全由 `levelInfo` 和 `CFG.skills[k].passive` 决定（`bingfa.js:126–134`：`skillOk` 对非被动技能看 `pfActive`）。现行规则下 C 的典型值 0～1，和 Code 量的“平均 0.47”同量级；方案 A 下 ≈ 2.5 + 0.3·军功 + 技能项 ≈ 3～6，对上中位 4.5。
`PFD`（`:323`）并入 (b)，不再单独多算整整一层（整层贵得多）。
兵法价 `:80`：`art(s)` 改为“兵法现在能用才值整数”——`artOpen`（第 N 回合起）没到、或背水的“车马炮比对方少”不满足时按 0.3 倍算；车马炮计数在 `score()` 现有循环里顺手数，O(1)。

### 3.3 怎么从 CFG / 引擎读规则

## 4. G4 · 引破釜 / 设陷阱（基本由 G1 带出来）

### 4.1 问题是什么

“引”和“拒”是同一笔账的两面：汉方要看到破釜之后的封锁期回报才会下饵（G1 的 b、c），楚方要看到同一回报才会拒饵。估值 `score(S, me)` 对两边对称（`:36`），搜索 `ab()` 对两边对称；所以 **G1 开了，G4 的“汉下饵”就有了**。楚方那一面差一点：楚根上核对破釜（`:440`）用 `d1 = depthDone − 1` 的深度、不加延伸，41 题里楚方核对时第 2 层静态搜索看不到汉 `车→3,9` 的将军——**楚会吃饵**。这不是新机制，就是把 G1(b) 的延伸也用在楚方根上。

### 4.2 方案（`BFAI_G4`，默认 1）

- 不做“主动下饵”的额外启发：搜索看得见就会下，看不见的饵本来也不该下。

### 4.3 CFG

同 G1；背水的门槛由 `CFG.beishui.on` 决定；“第 16 回合起”由 `pofuPairs` 返回空自动处理。

### 4.4 预计效果

## 5. 我们的分析里哪里错了或漏了

1. **“士象几乎不升”是错的，“升得被动”才对。** H24：汉 a2 75%、e2 50% 的局里升过。它们都是 `must`（被捉 / 被将军 / 两血子逼近）。少的是技能级（a4 10.7%、e3 11%、e4 0.7%）；而这在现行价目下**本来就不划算**（象 3→4 要 5 功换 +0.9 分和 0 血；静态 −0.53），Code 的军功实验也说改升级倾向只会变弱。**真缺口只有“升了立刻能用技能”这一条**，实战里稀少（146 步里 0 次），但一次就是一局。齐射 / 践踏 / 飞越 0% 更多是规则（象不能过河、践踏要在家门口吃到子）——要它们出场得改规则或价目，不是改电脑。

## 6. 优先级、顺序、相互影响

**顺序：G3 → G2 → G1 → G4。** G3、G2 规则无关、改动小、各自有一道明确的考题；G1 等背水 / 方案 A 的对照结果出来再定默认值（写法已通用，不用等）；G4 几乎是 G1 的附件。

**相互影响**（一起开会不会抵消）：
- G3 和 G2 都在**升级**上加分支：G3 在根（最多 +1 候选，稀少），G2 在第 2 层（只算升的那枚子自己）。两者叠加时第 2 层的 UPK 收窄（`:385–392`）对 G3 的候选照样生效，所以不会乘起来。
- G1(a) 省节点、G1(b) 和 G2 费节点，三个一起时汉方走子的平均节点大约持平、最坏 +15%【推断】——要实测。
- G1(c) 的估值项对两边对称，所以 G4（楚拒饵）和 G1（汉下饵）方向一致，不会一个让汉更敢、一个让楚更怕以致互相抵消——它们是同一个数。
- G1(a) 假设楚方按 `PF_MIN` 行事，G4 把楚方的门槛在背水下改成 2：那时 G1(a) 的 margin 也该跟着读同一个数（原型里把 `PF_MIN` 提成一个两处共用的函数 `pofuMargin()`）。
- 全关（四个都 0）时着法逐一同 dev——每个改动都在 `if (Gx)` 里，`score()` 的新项在 `pf === 0` 或 `G1 === 0` 时短路，`:80` 的兵法价条件化也在 G1 里。

**白话的顺序**：先让电脑在“升一级马上就能用上技能”的时候肯给士象花钱（G3），再让它会算“下回合进账再升”（G2），然后让它对破釜别那么草木皆兵、同时真能利用封锁期反击（G1），最后让楚方别吃明显的饵（G4）。
