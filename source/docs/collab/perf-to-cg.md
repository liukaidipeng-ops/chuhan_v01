# 优化部 → CG 组（最新的在最上面）

## Q1（10-10）预渲染视频用 `<video>` 播：坑和建议；胶片颗粒叠加层的代价

> 以下是经验判断，没有真机实测（优化部这里只有无头浏览器）。等 CG 组出第一段样片，我在 Ham 的 iPhone（15 或更新）和 TD 能找到的安卓机上核实。

**结论**：走预渲染视频，在性能上比实时三维省得多。手机都用专门的硬件解码 H.264，发热比实时画三维小得多。主要的坑在自动播放和微信内置浏览器，不在性能。

**编码**（照这个出片，低端机最稳）
- H.264 High 或 Main profile，level ≤ 4.0（低端安卓保守一点用 Main 3.1）；`yuv420p`；≤ 30 帧；720p。
- `-movflags +faststart`，让视频边下边播。
- 每段 ≤ 3 MB 可以。码率按 720p 约 1.5～2.5 Mbps 算，3 MB 大约 10～15 秒。
- 声音轨用 AAC，或者干脆不要，见下面“声音”一节。

**播放的坑**
1. **iOS 自动播放**：没声音的视频带 `muted` + `playsinline` 才能自动播。有声音的必须在玩家点击的同一个处理函数里调用 `play()`。中间隔了 `await`、定时器，就算“不是玩家点的”，`play()` 会被拒绝。
   → 建议：`play()` 的返回值要接住。被拒绝时显示“▶ 点击播放”，再给一个“跳过”。
2. **必须带 `playsinline`**（再加 `webkit-playsinline`），不然 iPhone 会自己全屏、跳出游戏。
3. **微信内置浏览器**（安卓旧内核）会把视频劫持成它自己的全屏播放器。要加 `x5-playsinline`、`x5-video-player-type="h5-page"`。iOS 微信有时要等 `WeixinJSBridgeReady` 以后才能播。Ham 的玩家很多从微信打开，这一条最要紧，出片后一定在微信里试。
4. **声音**：游戏的声音由 `audio.js`（声音部）管，第一次点击后已经“解锁”。建议视频静音播，配乐和音效由声音部用已解锁的通道按时间点放，这样自动播放最稳。要对齐时间，和声音部商量。
5. **解码器只开一个**：低端安卓同时能开的硬件解码器很少。同一时间只放一段；放完把 `src` 清空再 `load()`，把解码器和内存还回去。
6. **下载时机**：用 `preload="none"`，到结算前几秒或决战开始时再取。4G 下 3 MB 约 2～5 秒。没下完就跳过，别让玩家干等。文件放 `index.html` 旁边单独打包（和配音包一样），网址带版本号。
7. **放视频时停掉三维**：放过场时让 TD 把 `Core.render` 关掉（大厅盖着时就是这么做的）。不然显卡同时在画棋盘和放视频，这是最容易发烫的地方。

**胶片颗粒叠加层**
- 别用脚本每帧在画布上现生成噪点（`putImageData` 之类），低端机上这是全屏的 CPU 活，比放视频本身还费。
- 推荐：做一张 256×256 的噪点小图（WebP，几 KB），铺在视频上面一层 `div` 的背景里，用 CSS `animation` 加 `steps()` 每秒跳 12～24 次背景位置。整个过程不用脚本，由浏览器合成器做，代价很小。
- 别加 `mix-blend-mode`（正片叠底之类），用普通透明度（约 0.06～0.12）。混合模式要整屏多算一遍；页面上已经有一层全屏纸纹 `#paper` 在用 multiply，放过场时最好把它也藏掉。
- 颗粒别烧进视频：颗粒很难压缩，3 MB 的码率会被它吃掉，画面反而糊。你们“播放时叠加”的思路是对的。

**我能帮的**：样片出来后，我在无头浏览器里量叠加层的开销和三维停没停，真机部分请 Ham 用 iPhone 看一下发不发烫。
